# Build the replica-aware catalog nobody ships

Datacat's core model — a logical path namespace, dataset → numbered version → per-site replica, typed user metadata, and a readable filter language — is the right foundation, and no system reviewed here combines it with schemas, lineage, discovery and AI-asset tracking. The better system is therefore a successor that keeps Datacat's concepts and replaces its 2016 implementation; it is neither a patch to Datacat nor an extension of iRODS, Rucio or DataHub. The incumbents split cleanly: iRODS and Rucio know where bytes are but nothing about what is in them, while DataHub and the lakehouse catalogs know schemas and lineage but treat files as an opaque path prefix. Amundsen was archived in September 2026. Science projects bridge the split by running two catalogs synchronised over a message bus (Rubin, DUNE, SKA), and AI-for-science projects hand-maintain mirrors across HPC sites and Hugging Face. The unoccupied niche is a single transactional store that links physical replicas, logical datasets and their versions, and the models and evaluations built from them, with integrity, licence and takedown status propagating along the edges. The recommended shape is one stateless service on PostgreSQL with JSONB metadata validated against registered schemas, opaque stable IDs, and a transactional outbox feeding optional search and vector indexes. Every outward surface should be an existing standard (Iceberg REST, OpenLineage, Croissant, CloudEvents, OIDC, MCP). Three caveats apply: the Datacat findings come from a March 2016 snapshot that was read but not executed, much of the external evidence was seen only as search-result extracts, and no source demonstrates 10^10 file records in one catalog.

## Datacat got the concepts right and the plumbing wrong

### A compact model inherited from Fermi-LAT

Datacat is the REST generation of the catalog SLAC built for Fermi-LAT on Oracle and later generalised under the "SRS" name. The schema still carries Fermi-era columns such as `RunMin`, `RunMax`, `NumberEvents`, `ProcessInstance` and a ROOT-specific table ([hsqldb-schema.sql](/home/user/datacat/test/src/main/resources/org/srs/datacat/test/hsqldb-schema.sql)). The README defines the model in one sentence: "A Dataset consists of one or more versions of a file, each with one or more possible physical locations". Folders are POSIX-like directories, and Groups hold only datasets and act as a macro-dataset ([README.md](/home/user/datacat/README.md)).

The most distinctive idea is the **view**: a (version selector, site selector) pair with `current` and `canonical` defaults, so one identifier resolves to the right file for where the caller is ([DatasetView.java](/home/user/datacat/model/src/main/java/org/srs/datacat/model/DatasetView.java)). The database enforces sound invariants: unique names per parent, unique version IDs per dataset, one replica per site per version, and a unique physical path per site ([hsqldb-schema.sql](/home/user/datacat/test/src/main/resources/org/srs/datacat/test/hsqldb-schema.sql)). Registration is friendly to bulk loaders, because one POST creates node, version and locations and returns a distinct `409` with a `Location` header for each "already exists" case ([DatasetsResource.java](/home/user/datacat/rest/src/main/java/org/srs/datacat/rest/resources/DatasetsResource.java)). The filter language (`run > 6200 and runQuality =~ "GO*"`, plus `in` lists and ranges, `is null`, and sort and show fields over `*` and `**` container globs) is small and readable, and it binds values as SQL parameters ([README.md](/home/user/datacat/README.md), [DatacatSearchContext.java](/home/user/datacat/datacat-impl/src/main/java/org/srs/datacat/dao/sql/search/DatacatSearchContext.java)).

### The implementation defeats the model at scale

The checked-out code is a **March 2016 snapshot** (HEAD `274f2b0`, version `0.5-SNAPSHOT`): about 22,400 lines of Java 7 on Jersey 2.22 with a Python 2 client, roughly 58 Java tests, and 42 TODO markers ([pom.xml](/home/user/datacat/pom.xml)). Nothing was compiled or run, because the build depends on SLAC's internal Nexus. The defects below are therefore code-reading findings, and upstream `slaclab/datacat` may have fixed some of them. Upstream is in low-intensity maintenance, with build and CI commits as recent as October–November 2026 that nurse the code onto newer JDKs, and one notes that the public FreeHEP Maven repository returns 502 ([slaclab/datacat commits](https://github.com/slaclab/datacat/commits/master)).

Four structural choices limit the design. The first is **metadata storage**. User metadata lives in nine entity-attribute-value tables (three owner types × three value types), and every key in a filter adds another outer-joined sub-select ([MetajoinedStatement.java](/home/user/datacat/datacat-impl/src/main/java/org/srs/datacat/dao/sql/search/tables/MetajoinedStatement.java)). The typed table is chosen from the type of the literal in the query, so `run == '6200'` silently searches the string table and finds nothing if `run` was stored as a number ([SearchUtils.java](/home/user/datacat/datacat-impl/src/main/java/org/srs/datacat/dao/sql/search/SearchUtils.java)).

The second is **path resolution**. The catalog stores only name and parent, and it evaluates ACLs in Java. Search must therefore walk the folder tree in the application and insert each matching container, one row per round trip, into a `ContainerSearch` temporary table ([SearchUtils.java](/home/user/datacat/datacat-impl/src/main/java/org/srs/datacat/dao/sql/search/SearchUtils.java)). The third is **pagination**: the REST layer iterates the entire result stream to compute a count, with a default page size of 100,000 ([SearchResource.java](/home/user/datacat/rest/src/main/java/org/srs/datacat/rest/resources/SearchResource.java)). The fourth is **caching**. Path and ACL state live in a per-JVM soft-reference cache with a 60-second staleness window, marked "TODO: Get rid of this", which rules out consistent horizontal scaling ([DcFileSystemProvider.java](/home/user/datacat/core/src/main/java/org/srs/datacat/vfs/DcFileSystemProvider.java)).

Several subsystems are thinner than the README implies. The **path lock** added in the HEAD commit is prepared but never acquired, so concurrent writers are serialised only by database constraints ([SqlBaseDAO.java](/home/user/datacat/datacat-impl/src/main/java/org/srs/datacat/dao/sql/SqlBaseDAO.java)). Only the **MySQL-dialect DAO** is wired in, despite the claim of Oracle, MySQL and HSQLDB, and the two DAO families are near-verbatim 1,400-line copies ([App.java](/home/user/datacat/rest/src/main/java/org/srs/datacat/rest/App.java)). The **crawler** is a 110-line polling example that computes a CRC with the Unix `cksum` command ([crawler.py](/home/user/datacat/client/python/examples/crawler.py)). **Foreign metadata** consists of four hardcoded plugins, including one that points at a developer's personal schema ([SqlSearchDAO.java](/home/user/datacat/datacat-impl/src/main/java/org/srs/datacat/dao/sql/SqlSearchDAO.java)). The default **group lookup** puts every caller in `$PUBLIC$` only ([GroupManagerLookupService.java](/home/user/datacat/rest/src/main/java/org/srs/datacat/rest/security/GroupManagerLookupService.java)). **Non-latest versions** appear unreachable through the path API, because the join pins `latestversion` ([BaseDAOMySQL.java](/home/user/datacat/datacat-impl/src/main/java/org/srs/datacat/dao/sql/mysql/BaseDAOMySQL.java)).

The API has no rename or move, no delete of a single version or replica, no bulk endpoint and no OpenAPI description. Lineage, events, audit, soft delete, schema validation, replication rules and checksum verification are absent altogether.

Outside confirmation of adoption is modest. Search-result extracts tie the system to Fermi, EXO, CDMS, CTA simulation and an HPS instance at JLab ([HPS Data Catalog](https://confluence.slac.stanford.edu/spaces/hpsg/pages/180562091/Data+Catalog)). No rewrite or successor project was found. LSST DESC now documents a different registration tool, `lsstdesc-dataregistry` ([PyPI](https://pypi.org/project/lsstdesc-dataregistry/)). Porting the code to current platforms means `javax` → `jakarta`, replacing two unmaintained in-house libraries (`zerorm`, `freehep-lang`) and regenerating the parser. That effort is comparable to rewriting the server, which is why a successor is the better route than a refactor.

## Each incumbent solves half the problem

### iRODS and Rucio track bytes but describe them poorly

**iRODS** contributes the cleanest statement of logical/physical separation. A data object has one or more replicas on resources, each replica has its own state and checksum, and composable resource trees handle placement across POSIX, S3 and tape. Its weaknesses are the ones a successor must avoid.

**Metadata** is untyped attribute-value-unit string triples in a global EAV schema, with no nesting and no template enforcement. The authors of one workaround say this "may hinder the implementation of the FAIR principles" ([JSON2AVU paper](https://irods.org/uploads/2019/vanSchayck-Maastricht-JSON2AVU-paper.pdf)). The Metadata Templates Working Group concluded after years that the server should not manage templates at all ([WG lessons learned, UGM 2024](https://irods.org/uploads/2024/Russell-iRODS-iRODS_Metadata_Templates_Working_Group_Building_Blocks_and_Lessons_Learned-slides.pdf)).

**Policy** is the rule engine, which fires hooks around every server operation. It is powerful, but it sits in the request path and is hard to test. The declarative "policy composition" alternative reached only a **0.1.0 release in April 2026** ([iRODS dev update, April 2026](https://irods.org/2026/04/irods-development-update-april-2026/)).

**Scale** is bounded by the single relational catalog. The proven envelope is tens of petabytes and on the order of 10^8 objects per zone. Sanger manages 20 PB while still pinned to release 4.2.7 and repairing inconsistent replica states ([UGM 2024](https://irods.org/ugm2024/)). A zone with more than 110,000 users takes over five minutes to list `/zone/home` because of permission joins ([irods/irods#7045](https://github.com/irods/irods/issues/7045)). Finally, iRODS has no dataset, version, schema or lineage entities, and all I/O is proxied through its servers.

The project is alive (5.1.0 shipped in October 2026) but slow, and it defaults to MD5 checksums until iRODS 6 ([5.1.0 release](https://irods.org/2026/10/irods-5-1-0-is-released/), [dev update, April 2026](https://irods.org/2026/04/irods-development-update-april-2026/)).

**Rucio** is proven at a scale nothing else in open-source data management matches. The ATLAS instance holds "more than 1 exabyte of data, stored in a billion files, distributed over 120 data centres" ([rucio.cern.ch](https://rucio.cern.ch)). Its best idea is declarative replication: a rule states "N copies of this identifier on storage matching this expression until this lifetime", and asynchronous daemons converge storage toward it. Locks protect replicas, and tombstones turn unlocked replicas into a cache ([Barisits et al. 2019](https://arxiv.org/pdf/1902.09857)).

Its weakness is equally clear: **every major user pairs it with a second metadata system.** ATLAS uses AMI, CMS uses DBS, DUNE uses MetaCat and Rubin uses the Butler. CMS reports that "our metadata does not live in rucio, which makes filtering rules hard to create" ([CMS community report 2024](https://indico.cern.ch/event/1343110/contributions/6093893/attachments/2937877/5160663/CMSRucio%20Community%20Report.pdf)). Other limits follow from the design. Rucio's own **metadata** is fixed columns or schemaless JSON with comparison-only filters, and a "schema-governed catalog" was still a workshop proposal in November 2025 ([Rucio Workshop 2025](https://indico.cern.ch/event/1545309/contributions/)). Its **cost model** is per file, per replica and per lock, so hierarchical data and many small files fit poorly ([SKAO assessment 2024](https://indico.cern.ch/event/1343110/contributions/6089547/attachments/2937876/5160662/JSC%20-%20DDM%20Assessment%20-%20Rucio%20Workshop%2030-09-24%20(1).pdf)). Its **operational floor** is high: a 2025 European review calls the complexity "a significant obstacle for smaller scientific teams" ([JENA WP2 report](https://arxiv.org/pdf/2503.09213)). Its **security record** in 2026 includes fixes for remote code execution in the reaper daemon and command injection through file names ([Rucio releases](https://github.com/rucio/rucio/releases)).

### Amundsen and DataHub describe data but cannot place it

**Amundsen** is no longer a candidate. GitHub archived the repository on 29 September 2026 "due to inactivity", after a single commit in 2025 ([amundsen-io/amundsen](https://github.com/amundsen-io/amundsen)). It leaves two lessons: a small deployable core with usage-ranked search won early adoption, and a catalog without an extensible model and a sustaining organisation does not survive.

**DataHub** is the most complete open-source metadata platform, with v1.9.1 released on 19 November 2026 ([DataHub releases](https://github.com/datahub-project/datahub/releases)). Its durable ideas are worth copying. Entities are composed of independently written, schema-validated, versioned aspects. A relational store is the source of truth. A change log feeds every derived index ([metadata-model.md](https://github.com/datahub-project/datahub/blob/master/docs/modeling/metadata-model.md)). Its mistakes are just as instructive. The **minimum deployment is heavy**: a production install needs the metadata service, a frontend, SQL, Kafka and Elasticsearch or OpenSearch ([kubernetes.md](https://raw.githubusercontent.com/datahub-project/datahub/master/docs/deploy/kubernetes.md)). **Reindexing is fragile**: rebuilding derived search indexes is a recurring upgrade failure, with timeouts and jobs that never converge ([issue #16041](https://github.com/datahub-project/datahub/issues/16041), [issue #18949](https://github.com/datahub-project/datahub/issues/18949)). **Identity lives in names**: URNs are built from platform and name strings, so connector changes repeatedly orphan lineage, and DataHub's own Iceberg catalog sidestepped this with UUID URNs that persist "across renames" ([iceberg-catalog.md](https://raw.githubusercontent.com/datahub-project/datahub/master/docs/iceberg-catalog.md)). The **open-core boundary** excludes features a self-hosting lab would expect: usage-aware ranking, lineage-based propagation and fine-grained access control are Cloud-only ([Core vs Cloud](https://github.com/datahub-project/datahub/blob/master/docs/managed-datahub/managed-datahub-overview.md)).

For science, DataHub models files as "Datasets" with no replica, checksum or site concept. Its claimed proven scale of "10M+ assets" is one to two orders of magnitude below a file catalog's row count ([architecture.md](https://github.com/datahub-project/datahub/blob/master/docs/architecture/architecture.md)). No scientific file-cataloguing deployment of either system was found, though this is absence of evidence from a limited search.

### The wider landscape repeats the split

| System | Does well | Does badly | Status (Nov 2026) |
|---|---|---|---|
| Datacat | Dataset/version/replica model, views, filter language, group ACLs | EAV metadata, temp-table search, per-JVM cache, no lineage or events | Low-intensity maintenance |
| iRODS | Logical/physical split, replica state, tape and tiering, per-object ACLs | Untyped metadata, in-path rule engine, single-zone scale, no versions | Active, slow cadence |
| Rucio | Declarative placement at exabyte scale, self-healing, storage abstraction | Metadata, query, small files, hierarchy, operational floor | Active, clean-up releases |
| Amundsen | Simple install, usage ranking | Fixed model, no history or events | Archived |
| DataHub | Aspect model, change log, lineage, governance, MCP | Heavy stack, reindexing, name-based identity, no replicas | Very active |
| MetaCat (DUNE) | JSON metadata in Postgres, MQL set algebra, external-source joins | No replicas (Rucio), no UI or schemas | Active, small team |
| Rubin Butler | Dimension model, run collections, registry/datastore split | Direct-DB clients (REST retrofitted), no replicas, Python-coupled | In production |
| Gravitino / Unity Catalog | Filesets/volumes, models, credential vending | Path-prefix granularity; no per-file records, checksums or replica state | Active |
| Hugging Face Hub | Versioned repos, chunk dedup, Croissant at scale | Single provider, repo-level gating, free-text lineage | Dominant |
| lakeFS / DVC | Per-object versioning | No replica state or typed metadata queries | Active (lakeFS now stewards DVC) |

MetaCat is the closest science-side precedent for the metadata half. It is designed for "100 million files and beyond", and its query language supports named queries, provenance traversal and filters backed by external databases ([MetaCat paper](https://www.epj-conferences.org/10.1051/epjconf/202125102048), [MQL docs](https://fermitools.github.io/metacat/mql.html)). The Butler shows why clients must never reach the database directly: Rubin had to retrofit a REST server "for scaling and security reasons" ([DMTN-288](https://dmtn-288.lsst.io/DMTN-288.pdf)).

On the lakehouse side, the catalog API has converged on Iceberg REST, with credential vending and remote signing added in Iceberg 1.11 ([Iceberg 1.11.0](https://iceberg.apache.org/blog/apache-iceberg-1.11.0-release/)). Non-tabular objects remain governance handles there. Unity volumes are "intended for path-based data access only" ([Databricks volumes](https://docs.databricks.com/aws/en/volumes/)). Gravitino filesets gained multiple named locations in 1.0, the nearest lakehouse feature to replicas, but they are static directory alternatives without per-file state ([Gravitino 1.0.0 notes](https://gravitino.apache.org/blog/gravitino-1-0-0-release-notes)).

## The open niche spans replicas, datasets and models

### Science keeps building two catalogs and a bus

The strongest evidence for the niche is that large science projects compose it by hand. Rubin runs Rucio for file location and movement and the Butler for dataset search. A `rucio-register` tool pushes Butler datasets into Rucio, and a `ctrl_ingestd` daemon at each site consumes Kafka messages from a modified Rucio Hermes daemon to ingest arriving files into the local Butler ([Rubin Rucio–Butler integration](https://df-ops.lsst.io/usdf-applications/drp/rucio-butler-integration/index.html)). DUNE deliberately decomposed monolithic SAM into MetaCat, Rucio and a Data Dispatcher, and found the result "harder to test because it needs a local MetaCat instance and multiple Docker containers" ([DUNE CHEP 2024](https://indico.cern.ch/event/1338689/contributions/6010878/attachments/2952884/5191237/CHEP_2024_DUNE_Rucio.pdf)). ESCAPE and SKA called synchronising the metadata and replica catalogs "a strategic structural decision", and a May 2026 SKA talk still lists metadata handling and embargo control as adaptation work ([DIOS final meeting notes](https://indico.in2p3.fr/event/26928/attachments/70683/101471/ESCAPE%20DIOS%20Final%20Meeting-%20Draft%20Notes.pdf), [SRCNet talk](https://indico.cern.ch/event/1471803/contributions/6967407/)).

Research labs that adopt lakehouse technology take plain Iceberg REST with a light catalog and leave files outside it. STFC's 2026 study chose Lakekeeper ([STFC-TR-2026-011](https://epubs.stfc.ac.uk/manifestation/66674388/STFC-TR-2026-011.pdf)).

Three independent designs arrived at the same requirement: joining file metadata against small reference tables of runs, exposures or calibrations at query time. They are Datacat's foreign metadata, MetaCat's external filters and the Butler's dimension records. A successor should treat this as a core feature. It also shows that Datacat's least finished idea was its most forward-looking one.

### AI data adds layers that no file or table catalog models

AI data is a graph of immutable, versioned artifacts joined by derived-from, trained-on and evaluated-on edges. The artifacts include corpora, splits, shards, samples, labels, embeddings, indexes, checkpoints, adapters and evaluation results. Existing tools each cover a slice of this graph. Among **experiment trackers**, MLflow 3 made the logged model a first-class entity, but the link from an evaluation dataset to model metrics was still being tightened in MLflow 3.17 in October 2026 ([MLflow CHANGELOG](https://raw.githubusercontent.com/mlflow/mlflow/master/CHANGELOG.md)). In the **lakehouse**, Unity Catalog records lineage from training table to model only when a model is logged with `mlflow.log_input`, so it is opt-in and table-level ([Databricks docs](https://docs.databricks.com/aws/en/machine-learning/manage-model-lifecycle/)). Among **hubs**, Hugging Face separates immutable versioned repos from mutable, non-versioned Storage Buckets launched in March 2026, which signals that publication and working data need different semantics ([HF Storage Buckets](https://huggingface.co/blog/storage-buckets)).

Two kinds of indirection break the "one file = one record" assumption. LeRobotDataset v3 stores many robot episodes inside shared Parquet and MP4 shards and addresses them by metadata offsets ([LeRobot v3 docs](https://huggingface.co/docs/lerobot/lerobot-dataset-v3)). VirtualiZarr with Icechunk builds transactional Zarr stores out of chunk references into archival netCDF, HDF5 and FITS files without rewriting them ([VirtualiZarr](https://virtualizarr.readthedocs.io/en/latest/releases.html)). A catalog that tracks replicas must understand such manifests to keep the referenced bytes alive and co-located.

Scientific foundation-model datasets add **representation equivalence**. The Multimodal Universe (about 100 TB) ships native HDF5 at the Flatiron Institute, a mirror at NERSC, and per-survey Parquet copies on Hugging Face for streaming, all hand-maintained ([arXiv 2412.02527](https://arxiv.org/pdf/2412.02527)). These are the same logical version in different byte forms at different sites, a relationship no reviewed tool records.

Governance gaps are concrete. **Standards exist at the dataset level**: Croissant 1.1 (February 2026) added PROV-O provenance and machine-readable usage policies, and about 700,000 datasets carry it ([MLCommons](https://mlcommons.org/2026/02/croissant-1-1-standard/)). **Regulation demands dataset-to-model edges**: EU AI Act rules for general-purpose models have applied since 2 August 2025 and require a public summary of training content, which is in effect a report over dataset-version-to-model edges ([AI Act Service Desk](https://ai-act-service-desk.ec.europa.eu/en/resources)).

Enforcement mechanisms lag behind. **Signing stops at the artifact**: model signing covers files at rest but not training-data provenance ([IETF draft-sharif](https://datatracker.ietf.org/doc/html/draft-sharif-ai-model-lifecycle-attestation-00)). **Contamination control is voluntary**, relying on canary strings and post-hoc statistical tests ([arXiv 2502.17521](https://arxiv.org/pdf/2502.17521)). **Takedown is manual**: no tool or standard was found that propagates a retraction from a dataset to derived shards, embeddings and checkpoints.

### The niche, stated precisely

The unoccupied position is an open-source catalog that is small to deploy and has three properties. Its **core** is logical dataset → immutable versions → checksummed replicas across sites, with schema-registered typed metadata and reference tables, queryable at 10^8 or more files. Its **graph** holds representations, views, sample manifests, models and evaluations in the same store. Its **faces** are data-science standards at every outward interface.

Gravitino is nearest from the lakehouse side, and MetaCat+Rucio and Butler+Rucio are nearest from the science side. Neither spans both.

The steelman against building is real. Extending Gravitino with per-file state, or adding schemas and lineage to MetaCat, would reuse live communities. Internal systems at large AI labs may already solve parts of this without public write-ups. The case for a new core rests on one architectural bet: logical identity, metadata and replica state belong in a single transactional store. Neither retrofit path makes that bet, and each two-system composition has paid for avoiding it in synchronisation glue.

The new system should not compete as a table catalog or a transfer engine. Both fields are consolidating around Iceberg REST and around FTS, Globus and Pelican respectively.

## One Postgres-backed service with standard outward faces

### Recommended data model

**Identity.** Every entity gets an opaque, immutable ID (UUIDv7 or similar). The hierarchical path becomes a mutable, indexed alias. Foreign identifiers are stored as first-class aliases: Rucio `scope:name`, `catalog.schema.name`, OpenLineage namespace+name, Hugging Face revisions, OCI digests and DOIs. This inverts both Datacat (name+parent is the key) and DataHub (the URN encodes platform and name).

**Naming.** Datacat's vocabulary should change. Its "Dataset" (one file with versions) becomes a **File**. Its "Group" becomes a **Dataset**, a versioned collection. Datacat's Dataset collides with the meaning every data-science and AI tool gives the word.

**Two cost tiers.** The model separates rich entities from cheap ones, following the main lesson of the DataHub analysis. The **rich tier** (10^5–10^7 rows) holds Containers, Datasets, DatasetVersions, Tables, Models, EvalSuites, Runs, Sites and Schemas; these carry independently versioned aspects and are indexed for search. The **cheap tier** (10^8–10^9+ rows) holds FileVersions and Replicas in narrow, partitioned relational tables that are queried relationally.

**Dataset versions and files.** A DatasetVersion is an immutable manifest of FileVersions with a manifest digest that can be signed. A mutable "working" state with an explicit publish transition mirrors the Hugging Face split between buckets and repos. A FileVersion carries its size and a set of (algorithm, value) checksums. The set matters because sites differ: Rubin's French and UK facilities record adler32 at file creation, the US facility does not, and computing checksums at registration is a measured bottleneck ([Rubin multi-site data movement](https://www.amlight.net/wp-content/uploads/2026/01/SA3CC2026_-Rubin-Multi-site-Data-Movement-Wei-Yang.pdf)).

**Replicas and sites.** A Replica is a (FileVersion, Site) pair with a URL, storage class (including tape and cache tiers), last-verified time and a state machine: registered → verified → suspect → lost or retired. Verification work is leased so two crawlers at one site do not double-process. A Site carries protocols and key-value attributes that expressions can address, as Rucio's storage elements do. It can optionally have a deterministic path function, which removes a class of catalog/storage drift.

**AI layers.** Four constructs sit above the file layer. A **Representation** groups the files of one physical form of a dataset version (native HDF5, Parquet, WebDataset tar, tokenized shards). A `materialized_from` edge records the transform parameters, and replicas are byte-identical only within a representation. A **View** is (base versions, predicate or explicit sample list, digest of the resolved manifest), which gives no-copy subsets and splits.

**Samples** get stable logical IDs plus per-representation locators (file digest and row, offset or chunk key). They are stored as columnar manifest files that the catalog registers, never as rows in the transactional store, with exact and MinHash fingerprints alongside. **Lineage** follows W3C PROV. Runs are activities, and `used` edges carry a role (train, validation, test, retrieval); that role makes contamination queries possible. Models link by `fine_tuned_from` and `quantized_from`, and EvalResults link a model to a dataset version.

Embeddings, indexes and loader shards are derived materialisations: rebuildable, tied to a source version, and garbage-collectable.

**Metadata.** Each entity holds a JSONB document validated against schemas registered per data type, with declared types and units. Declared keys are promoted to typed, indexed columns so range predicates and sorts do not depend on GIN indexes, which serve only equality and containment ([PostgreSQL GIN](https://www.postgresql.org/docs/current/gin.html)). Reference ("dimension") tables are first-class catalog objects joinable in queries. This is the generalised, runtime-configured form of Datacat's foreign metadata.

**Policy.** ACLs stay Datacat-style: group-based and inherited from containers, never one row per file. The model adds user principals, time-based embargo and defined ancestor semantics. Licence and consent terms are machine-evaluable, attached to datasets and sources, and propagate along derivation edges with conflicts flagged. Tombstones on versions and samples propagate forward to every derived dataset, index, checkpoint and evaluation.

**Placement.** Rules are data (selector over metadata, site expression, copy count, lifetime) with locks and tombstones as in Rucio. Because rules live in the same store as the metadata, they can key on it. That closes the gap CMS described.

### Architecture

**Core service.** The evidence favours one stateless service with PostgreSQL as the only required dependency. Postgres-only or Postgres-first designs carry MetaCat, the Butler registry, Marquez, OpenMetadata and pgstac. The pgstac README states it is "used in production to scale to hundreds of millions of STAC items" ([pgstac](https://github.com/stac-utils/pgstac/)). Its documented failure modes are exact counts and unbounded sorts on huge result sets, the same ones Datacat has, so the API should use cursor pagination with a stable default order and offer estimated counts only ([stac-fastapi-pgstac](https://github.com/stac-utils/stac-fastapi-pgstac)).

**Paths and permissions in SQL.** Materialised paths (`ltree`) and ACL evaluation in SQL remove the tree walk and the temporary table. An embedded SQLite mode with the same schema subset serves laptops, tests and static exports, following the pattern of Lance directory namespaces and STAC static catalogs. The embedded mode and `ltree` at catalog scale are design inferences without production evidence for a file catalog.

**Write path and change feed.** Writes are synchronous transactions that also append to an outbox table. The outbox is published as CloudEvents and feeds optional projections: OpenSearch or an embedded index for text, pgvector for embeddings at dataset level, and a Kafka or NATS bridge only where a site already runs one. Search and graph projections need online rebuild (new index, dual write, verify, alias swap) as a tested subsystem from the start. No class of metadata should live only in a derived index.

**Data path.** The catalog brokers access and stays out of the data path. It returns signed URLs or vended, prefix-scoped credentials and exposes an fsspec filesystem. Bulk registration, streaming results as Arrow or NDJSON, and exportable manifests are day-one features, so 10^5 batch jobs do not each query the service.

**Background work.** Site-local crawler agents claim leased verification and extraction tasks. A reconciler evaluates placement rules and delegates execution to pluggable movers (FTS, Globus, rclone, Pelican). Format extractors for FITS, HDF5, ROOT, safetensors and GGUF are runtime-registered plugins.

**Query and agents.** The query language keeps Datacat's surface and adds MetaCat-style set algebra, named queries and lineage traversal, compiled to SQL. An MCP server sits on the same API and executes with the caller's identity, as OpenMetadata's does ([OpenMetadata](https://open-metadata.org/llms.txt)).

**Scale.** 10^8 file rows on one tuned Postgres is demonstrated elsewhere. 10^10 is not demonstrated anywhere reviewed. Partitioning by namespace should be in the first schema, and cold per-file rows should be able to live in columnar manifests.

### Standards to adopt

No standard exists for the core (a logical file with versions and checksummed replicas across sites). Standards exist for nearly every edge.

| Surface | Adopt | Role |
|---|---|---|
| Tables | Iceberg REST catalog | Expose or front tabular assets; surface each collection as a table of files |
| Lineage | OpenLineage in, W3C PROV out | Operational ingest; archival export. The symlinks facet maps physical URLs to logical IDs |
| Dataset description | Croissant 1.1, schema.org/Dataset, DCAT 3 | One JSON-LD generator; import and export |
| Packaging and citation | RO-Crate, DataCite DOIs | Publication tier |
| AI governance | SPDX 3 AI/Dataset profiles, CycloneDX ML-BOM, OpenSSF model-signing manifests | Generated from the lineage graph; signed version manifests |
| Auth | OIDC with WLCG/SciTokens profiles; ReBAC or Cedar policy engine | Capability scopes map onto path prefixes |
| Events and schemas | CloudEvents; JSON Schema authored via LinkML | Change feed; metadata validation |
| Access | fsspec URLs, RFC 9530 digests, signed URLs | Notebook and HTTP access |
| Agents | MCP | Search, describe, resolve, lineage and policy-check tools |
| Domain facades | STAC, IVOA TAP/ObsCore/DataLink | Optional read-only projections |

One timing fact shapes the auth design. The WLCG phase-out of X.509 has slipped to 2028-Q1, and "most experiments are still using x.509 for storage auth". The system must support certificate-fronted storage alongside tokens for several more years ([WLCG token progress, Sept 2025](https://indico.cern.ch/event/1566166/contributions/6688798/attachments/3141551/5576025/WLCG_Token_Progress-250924.pdf)).

### What to keep, fix and drop from Datacat

| Verdict | Items |
|---|---|
| Keep (concepts) | Logical namespace decoupled from storage; version and replica pointers ("latest", "master"); the view abstraction; groups as macro-datasets; typed metadata with merge-patch and null-deletes; filter language surface and container globs; group-based inheritable ACLs with an effective-permissions call; scan-status contract for site crawlers; single-call create with precise conflict codes; container statistics |
| Fix (new implementation) | EAV tables → JSONB with schema registry and promoted keys; name+parent → opaque IDs plus materialised paths; Java-side ACL and temp-table search → SQL; in-JVM lock and cache → database transactions and an event-invalidated optional cache; old versions fully addressable, with single-version and single-replica retirement and tombstones; checksums as (algorithm, value) strings; replica state machine with leases; cursor pagination; query parameters or sub-resources in place of matrix parameters (`;v=3;s=SLAC`); OpenAPI; bulk and rename endpoints; runtime-configured plugins; a client independent of server modules; CLI parity |
| Drop | Fermi-era fixed columns (model them as metadata); the faux-NIO VFS layer and soft-reference cache; duplicated per-dialect DAOs and reflection-driven patch SQL; `zerorm`, `freehep-lang` and the SRS parent POM; experiment plugins in core; XML and plain-text representations unless a consumer exists; HMAC-SHA1 signing in favour of OIDC bearer tokens |
| Add | Lineage, events, audit and soft delete, placement rules, checksum verification policy, full-text and faceted search, a web UI, migrations, container deployment, metrics |

## A five-phase path, with placement last

The phasing below is a recommendation synthesised from the evidence. It is ordered so each phase is useful alone and the riskiest assumptions are tested first. It carries no time estimates because none of the sources support them.

**Phase 0: verify and specify.** Diff upstream `slaclab/datacat` master against the 2016 snapshot before treating any listed defect as current. Write the core model as a schema, with conformance tests that both the server and embedded modes must pass. Choose one anchor science user and one AI-dataset user. Science-side adoption has historically come from one anchor experiment with a generic design, as MetaCat had with DUNE.

**Phase 1: core catalog.** Build the Postgres schema (containers, files, versions, replicas as plain records, typed JSONB metadata), the single API with cursor pagination and bulk registration, the Datacat-compatible filter language compiled to SQL, a Python 3 client and CLI, and an importer from an existing Datacat database. Ship the SQLite mode here. Exit when a real Datacat instance imports cleanly and a synthetic 10^8-file load answers metadata queries acceptably. This is the first place the Postgres-JSONB bet can fail, and no head-to-head benchmark at this scale was found.

**Phase 2: replicas and integrity.** Add the site registry, the replica state machine, leased crawler and extractor agents, multi-algorithm checksums with lazy backfill, the outbox change feed, signed-URL and credential brokering, and the fsspec filesystem. Exit when two sites stay consistent without manual repair and a downstream consumer can follow the event stream.

**Phase 3: data-science faces.** Add the schema registry, immutable dataset versions with signed manifests and the working-to-published transition, reference tables, OpenLineage ingest with file-level parentage, the search projection with online rebuild, a discovery UI, an Iceberg REST facade for tables-of-files, and Croissant/DCAT export. Exit when a notebook user can find a dataset by search and open it by name without knowing its site.

**Phase 4: AI layer.** Add representations and views, sample manifests and fingerprints, model and evaluation entities with role-typed usage edges, licence propagation, takedown traversal, contamination queries, AIBOM and training-summary report generation, and the MCP server. Novelty should be re-verified here against current DataChain, Lance namespace and lakeFS releases, which could not be checked.

**Phase 5: placement and federation.** Add declarative replication rules with locks, lifetimes and quotas, a reconciler with pluggable transfer executors, tape and cache-tier storage classes, pre-staging for scheduled training runs, DOI minting, and federation between instances.

Placement comes last deliberately. Until then the system can register replicas that Rucio, Globus or a site's own tools create. Rucio's rule engine took a decade of operations to harden, and its reconciliation loop is permanently busy: ATLAS reported about 200,000 failed transfers a day against more than a million successful ones in 2023 ([ATLAS Data Flows & Rucio](https://indico.cern.ch/event/1252369/contributions/5515384/attachments/2734461/4754446/ATLAS%20Data%20Flows%20&%20Rucio.pdf)). Reaching Rucio's placement maturity is the most expensive goal on the list and the one adopters need least on day one.

## Conclusion

The two-tier cost model is the hinge of the whole design. Science catalogs fail data scientists because they stop at the file. Enterprise catalogs fail scientists because every entity is expensive. A system that keeps a billion cheap file and replica rows beside a few million rich, searchable, lineage-bearing entities can serve both. It also turns AI governance into queries over one graph: training-content summaries, contamination checks and takedown become traversals, with no reconciliation across MLflow, a hub and a replica manager.

The research also changes how Datacat itself should be read. It is not an obsolete system to be replaced by an industry catalog. It is a correct small core that was never given a schema registry, an event log, or standard outward faces. Its weakest subsystem, foreign metadata, anticipated a requirement that MetaCat and the Butler later confirmed independently. Two risks should be retired before committing heavily: whether JSONB with promoted keys holds at 10^8–10^9 files on the anchor user's real queries, and whether an anchor user exists at all. The second matters more. Amundsen was archived for lack of a sustaining organisation, and the science-side survivors each grew around one committed experiment.

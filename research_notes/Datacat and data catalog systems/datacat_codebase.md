## 1. Data model: Datasets, Versions, Locations, Folders, Groups, views, metadata types

### Takeaway
Datacat models a POSIX-like tree of containers (Folders, and Groups that hold only datasets) whose leaves are Datasets; each Dataset has integer-numbered Versions, each Version has per-site Locations (replicas), and user metadata (string / number / timestamp) hangs off Versions and containers in three typed EAV tables per owner type. The SQL schema is inherited from the Fermi/GLAST-era catalog (legacy columns such as RunMin/RunMax/NumberEvents, ProcessInstance, TaskName, a ROOT-specific table) and stores no materialised path, only name + parent.

### Inferences
- There are three partly overlapping metadata layers: fixed columns inherited from Fermi (run range, event count), typed EAV user metadata, and "foreign" tables joined at search time. A successor should treat run range / event count as ordinary metadata.
- Metadata is attached to the **version**, not the dataset or the replica, so re-versioning a file drops its metadata unless the client re-sends it; replica-level facts (size, checksum, scan status) are fixed columns and cannot be extended.
- Changing a key's type leaves the old value behind: merge only updates the table for the *new* type and inserts there if absent, and the unique constraint is per table, so the same key can exist in two typed tables for one version (consistent with `DatasetMetaInfo` allowing several types per name). Readers put all three tables into one map, so which value wins is order-dependent.
- No dataset-level `dateModified` column exists; `VerDataset` only has `Registered`. The model's `getDateModified()` has nothing durable behind it.
- Because only `(Name, Parent)` is stored, every path resolution is a walk from the root, and renames/moves would be cheap in SQL — but no move/rename operation exists anywhere in the DAO or REST layers.
- PKs come from one shared sequence on HSQLDB (`dataset_seq`) but from per-table `SERIAL` on MySQL, so a pk is globally unique in one dialect and only table-unique in the other.

### Gaps
- No Oracle table DDL is in the repo, so the production (Oracle) schema at SLAC could differ from the HSQLDB/MySQL test schemas; I could not check.
- Row counts / catalogue sizes in production deployments are not in the repo.

## 2. Architecture: modules, VFS layer (caching, locking), datastore interface, supported databases

### Takeaway
The server is a seven-module Maven build (~22.4k lines of Java, 177 files) layered as REST resources → `DcFileSystemProvider` ("VFS": path resolution, ACL checks, in-JVM cache) → DAO interfaces → hand-written JDBC SQL. In this snapshot the "java.nio-style VFS" is a design idiom rather than a real `FileSystemProvider`, the path lock is never actually acquired, and only the MySQL-dialect DAO is wired in (it is also what the HSQLDB tests run), despite the README naming Oracle, MySQL and HSQLDB.

## 3. Search: query language, SQL translation, metadata predicates, container targets, temp tables, scaling limits

### Takeaway
Search = (container target glob) + (boolean filter string) + optional sort/show fields. The filter is parsed by the external `freehep-lang` parser into an AST, which is translated with the external `zerorm` SQL builder into one SELECT over dataset/version/location with one outer-joined EAV sub-select per metadata key; container targets are resolved in Java by walking the VFS (with ACL checks) and then inserted row-by-row into a `ContainerSearch` temporary table that the SELECT joins. It is workable for modest trees but has structural scaling limits: full subtree walks, per-request temp-table loads, EAV self-joins, and count-by-full-iteration pagination.

### Inferences
- **Why temp tables are needed**: (a) the catalogue stores only name + parent, so SQL cannot filter by path or glob; (b) per-container READ permission is evaluated in Java against cached ACL strings, so the authorised container set must be computed outside SQL; (c) that set can be large (every folder under `/**`), too large for an `IN (...)` list (Oracle caps those at 1,000 literals); (d) the temp table doubles as the carrier of each container's path string for building result paths. A successor with a materialised path / closure table / ltree and ACL evaluation expressible in SQL would not need it.
- Scaling limits implied by the design:
  - A `/**` target visits every folder in the subtree and loads each folder's child list (one query per folder plus the per-child follow-up queries noted in section 2) on a cold cache, before any dataset SQL runs.
  - Row-at-a-time inserts into the temp table: one round trip per matched container, per request; on MySQL also a DROP + CREATE per request.
  - Each metadata key in filter, sort or show adds another outer-joined EAV sub-select; the join key is the version pk and the only helpful index is `(MetaName, MetaValue)`.
  - Offset pagination with a full scan to count means page N costs the same as the whole query; with no default ORDER BY, pages are not guaranteed stable between requests.
  - The `OR` in the outer join condition (folder pk OR group pk) tends to defeat index use on many optimisers.
  - Per-request rebuild of the metadata-name context scales with the number of distinct metadata keys in the whole catalogue.
- Type-by-literal table selection has a usability trap: `run == '6200'` searches the string table and silently finds nothing if `run` was stored as a number; conversely a key stored with both types is searched only in the table matching the literal.
- Grouping result rows by adjacent `datasetversion` assumes rows of one version stay adjacent. With a user sort on a non-unique key and several locations per dataset, a database is free to interleave equal-key rows, which would split one dataset into duplicates. `rs.getInt("datasetversion")` is also compared with a `long` pk, a truncation risk above 2^31.
- Predicates cannot span versions or replicas ("has a replica at A but not at B"), there are no aggregates/facets, no full-text or substring index (only `LIKE`), and no saved queries.
- Metadata `LEFT OUTER JOIN` + predicate in `WHERE` behaves as an inner join for ordinary comparisons but is what makes `is null` ("key absent") work.

### Gaps
- The authoritative grammar lives in `freehep-lang` (not in this repo; `java.freehep.org/maven2` — upstream's Oct 2026 commit message says that host returns 502). Operator precedence and timestamp literal syntax were inferred from the PLY prototype and tests, not from the real grammar.
- `zerorm` (SQL builder, v0.2) is likewise external; I could not inspect how it renders dialect differences.
- No performance numbers exist in the repo; the limits above are structural reasoning, not measurements.

## 5. Security: ACL model, authentication/authorisation pluggability, group manager

### Takeaway
Authorisation is a small AFS-inspired ACL: group-only entries of the form `name@project:g:<perms>` with five permissions (`r i d w a`), stored as a comma-separated string in a column on each folder/group and evaluated in the VFS layer as "any ACL entry whose group the caller belongs to grants the permission". Authentication is entirely external (whatever sets the servlet `SecurityContext`), and the "GroupManager" integration in this repo is a stub that puts every caller in `$PUBLIC$` only.

### Cited Findings
- Permissions enum `READ(r) INSERT(i) DELETE(d) WRITE(w) ADMIN(a)`; `check(groups, acl, permission)` returns true if any entry's subject is in the caller's group set and contains the permission; `effective()` returns the packed union — [model/J/model/security/DcPermissions.java](/home/user/datacat/model/src/main/java/org/srs/datacat/model/security/DcPermissions.java)

### Inferences
- **Probable bug**: because the `instanceof … Builder` test can never be true for a built object, setting an ACL on a *group* issues `UPDATE DatasetLogicalFolder SET ACL=? WHERE DatasetLogicalFolder=<group pk>`. On MySQL (per-table auto-increment) that would overwrite the ACL of an unrelated folder that happens to share the numeric pk; on HSQLDB (shared sequence) it would update nothing. Not confirmed by execution.
- Authorisation checks only the target (or its parent), not every ancestor: READ on `/a/b/c` does not require READ on `/a`. Inheritance softens this (children without their own ACL copy the parent's), but an explicit permissive ACL deep in the tree is reachable by direct path even if an ancestor is restrictive. Search differs: it walks from the base and silently skips denied subtrees.
- ACLs are cached inside `DcFile` objects, so on other JVMs (and for descendants that inherited the old ACL, which are not evicted when a parent's ACL changes) a revocation can lag by the cache lifetime.
- Group-only, positive-only ACLs with five verbs are easy to reason about and a good match for SSO group membership; missing pieces are user principals, deny entries, per-dataset ACLs (the `VerDataset.ACL` column is `varchar(40)` and the API refuses dataset ACLs), ownership, tokens/scopes and audit logging.
- The HMAC scheme (SHA-1, shared secret, AWS-v2 style) is verified by something outside this repo — presumably the SRS web framework/servlet container at SLAC.

### Gaps
- The real GroupManager integration and the server-side HMAC/SSO verification are not in this checkout; how production resolved groups is unknown from code.
- Whether `$PROTECTED$` is granted to any authenticated user is not visible (it is added only in the `getPermissions(…, group)` helper).

## 9. Strengths, weaknesses, and what a successor should keep, fix and drop

### Takeaway
The concepts are sound and compact — logical path namespace, dataset → version → per-site replica, typed user metadata, a (version, site) "view", group-scoped ACLs, a readable filter language, crawler-by-scan-status — and are worth carrying forward almost unchanged. The implementation choices around them (EAV metadata with duplicated hand-written SQL, path resolution and ACL evaluation in a per-JVM cache, temp-table search, matrix-parameter URLs, niche in-house libraries, hardcoded experiment plugins) are what a successor should replace.

### Cited Findings
- Compact layered design with a storage-agnostic DAO boundary: five small interfaces define the whole datastore contract — [model/J/dao/](/home/user/datacat/model/src/main/java/org/srs/datacat/dao)
- Idempotent-friendly registration: one POST can create node + version + locations, with distinct conflict codes and `Location` headers for each "already exists" case, and `MERGE_*` / `SKIP_*_CHECK` options for bulk loaders — [DatasetsResource.java:139-300](/home/user/datacat/rest/src/main/java/org/srs/datacat/rest/resources/DatasetsResource.java), [DatasetOption.java](/home/user/datacat/model/src/main/java/org/srs/datacat/model/dataset/DatasetOption.java)
- Database-enforced invariants: one parent per dataset (CHECK), unique names per parent, unique version ids per dataset, one replica per site per version, unique physical path per site — [hsqldb-schema.sql:98-181](/home/user/datacat/test/src/main/resources/org/srs/datacat/test/hsqldb-schema.sql)
- Search binds user values as parameters and validates identifiers against known columns/metadata names before building SQL — [DatacatSearchContext.java:89-98, 193-198](/home/user/datacat/datacat-impl/src/main/java/org/srs/datacat/dao/sql/search/DatacatSearchContext.java)
- Streaming result iteration from JDBC cursors to the REST layer (`DirectoryStream`) rather than materialising in the DAO — [SearchUtils.java:312-376](/home/user/datacat/datacat-impl/src/main/java/org/srs/datacat/dao/sql/search/SearchUtils.java)
- Weaknesses are documented with sources in sections 2–7: no-op locking ([SqlBaseDAO.java:58-67](/home/user/datacat/datacat-impl/src/main/java/org/srs/datacat/dao/sql/SqlBaseDAO.java)); per-JVM 60-second cache ([DcFileSystemProvider.java:71](/home/user/datacat/core/src/main/java/org/srs/datacat/vfs/DcFileSystemProvider.java)); duplicated DAO dialects ([dao/sql/mysql/](/home/user/datacat/datacat-impl/src/main/java/org/srs/datacat/dao/sql/mysql)); temp-table search ([SearchUtils.java:260-290](/home/user/datacat/datacat-impl/src/main/java/org/srs/datacat/dao/sql/search/SearchUtils.java)); count-by-iteration paging ([SearchResource.java:99-110](/home/user/datacat/rest/src/main/java/org/srs/datacat/rest/resources/SearchResource.java)); stub group lookup ([GroupManagerLookupService.java](/home/user/datacat/rest/src/main/java/org/srs/datacat/rest/security/GroupManagerLookupService.java)); hardcoded plugins ([SqlSearchDAO.java](/home/user/datacat/datacat-impl/src/main/java/org/srs/datacat/dao/sql/SqlSearchDAO.java))

### Inferences

Keep (concepts)
- Logical hierarchical namespace decoupled from physical storage; dataset → immutable-ish numbered versions → one replica per site; "latest version" and "master replica" as explicit pointers.
- The **view** abstraction (version selector × site selector, with `current`/`canonical` defaults) — it lets one identifier resolve to "the right file for where I am".
- Groups as "containers of datasets only", i.e. a macro-dataset unit that can carry its own metadata and stats.
- Typed user metadata (integer / decimal / string / timestamp) with merge-patch and null-deletes semantics; metadata on containers as well as files.
- The filter language's surface (`and`/`or`, comparisons, `in` lists and ranges, `=~` globs, `is null`), plus sort and "show these extra fields" options, and target globs with `*` / `**`.
- Group-based, inheritable ACLs with a small verb set and a separate "what are my effective permissions here" call.
- The scan-status contract for site-local crawlers, and the foreign-metadata *idea* of joining domain tables at query time.
- Container stat views (child counts; dataset count, bytes, events).
- Single-call create of dataset + version + replica with precise conflict reporting.

Fix (keep the feature, change the implementation)
- Metadata storage: replace nine EAV tables with a typed JSON document column (e.g. PostgreSQL `jsonb` + GIN / expression indexes) or one typed-EAV table, with an optional schema registry per data type so keys have declared types, units and validation.
- Paths: store a materialised path or closure/ltree so glob targets and subtree queries run in SQL; then search needs no VFS walk and no temp table.
- Authorisation: evaluate ACLs in the database or via a path-prefix policy store so search and listing filter in one query; define ancestor-traversal semantics explicitly; add user principals, tokens and audit.
- Concurrency and caching: rely on DB transactions/constraints (or real row locks) rather than an in-JVM lock map; make any cache optional, bounded and invalidated by a change feed so the service can scale horizontally.
- Versions: make non-latest versions fully addressable; allow deleting/retiring a single version or replica with tombstones; decide whether metadata belongs to the dataset, the version or both.
- Replicas: add checksum algorithm + value as strings, storage endpoint/protocol (URL), replica state machine (registered → verified → lost/retired) with leases for crawlers, and timestamps that are real.
- Pagination: keyset/cursor pagination with a stable default order and an optional, separate count.
- API surface: query parameters or sub-resources instead of matrix parameters and `.json` suffixes; an OpenAPI description; bulk endpoints; rename/move; lookup-table (site, format, data type) management endpoints; unversioned base URL with versioned media types or `/v1`.
- Extensibility: runtime-registered plugins (configuration, not compiled-in classes) for foreign metadata and for file-format extractors.
- Clients: a client library that does not depend on server modules; Python 3; CLI parity with the API (patch, mkver, mkloc, ACL edit).

Drop
- Fermi-era fixed columns (`RunMin`, `RunMax`, `NumberEvents`, `ProcessInstance`, `TaskName`, `VerDatasetMetaRoot`, `CrawlerPriority`) and numeric CRC checksums — model them as metadata.
- The faux-NIO VFS layer and soft-reference cache as the place where permissions and path logic live.
- Per-dialect copy-pasted DAOs, reflection-driven `@Patchable` SQL generation, the `zerorm`/`freehep-lang` in-house dependencies and the SRS parent POM/Nexus coupling.
- Experiment-specific plugins in core (`EXORunIndex`, `jgates_fitsTest.*`), the stale SPI file, XML and text/plain representations (unless a concrete consumer exists), HMAC-SHA1 request signing in favour of standard OIDC/OAuth2 bearer tokens.

Add (absent today and expected of a successor)
- Lineage/provenance (dataset-to-dataset and dataset-to-process relations), event/notification stream, audit history and soft delete, replication rules and transfer orchestration hooks (or integration with an external mover such as Rucio/FTS/Globus), checksum verification policy, full-text and faceted search, a web UI, migrations, container-native deployment, and metrics.

### Gaps
- These recommendations are derived from the March 2016 snapshot; upstream may already have addressed some "fix" items (for example Python 3 support has been, per 2023 commit titles). A diff against `slaclab/datacat` master is needed before treating any specific defect as current.
- No user feedback, issue-tracker history (the `SDC` JIRA project) or operational post-mortems were available to weigh which weaknesses actually hurt in production.

## Addendum: how registration over HTTP handled existing entries

Added November 2026, from a second read of the REST and DAO code, for the design of registration commits in mudcat.

Datacat registered one dataset per `POST`. The outcome depended on a comparison of the request with the stored state, expressed in HTTP status codes.

- **The target of the request decided the work.** `DatasetsResource` derives a set of `DatasetOption` values from the kind of target and the payload: a `POST` to a folder or group adds `CREATE_NODE`; a version in the payload adds `CREATE_VERSION`; locations add `CREATE_LOCATIONS`. If locations are given without a version, the version is set to `NEW_VERSION` — [rest/src/main/java/org/srs/datacat/rest/resources/DatasetsResource.java:161-183](/home/user/datacat/rest/src/main/java/org/srs/datacat/rest/resources/DatasetsResource.java).
- **Options.** `CREATE_NODE`, `CREATE_VERSION`, `CREATE_LOCATIONS`, `MERGE_NODE`, `MERGE_VERSION`, and three optimisations that skip existence checks: `SKIP_NODE_CHECK`, `SKIP_VERSION_CHECK`, `SKIP_LOCATION_CHECK` — [model/src/main/java/org/srs/datacat/model/dataset/DatasetOption.java](/home/user/datacat/model/src/main/java/org/srs/datacat/model/dataset/DatasetOption.java).
- **Existing node.** `SqlDatasetDAO.createDataset` looks the name up in the parent. If it exists and `MERGE_NODE` is not set, it throws `DATASET_EXISTS`; with `MERGE_NODE` it patches the node. If it created the node, it skips the version check — [datacat-impl/src/main/java/org/srs/datacat/dao/sql/SqlDatasetDAO.java:60-90](/home/user/datacat/datacat-impl/src/main/java/org/srs/datacat/dao/sql/SqlDatasetDAO.java).
- **Versions.** `createOrMergeDatasetVersion` compares the requested version ID with the current one. Without merge, `getCreationVersionID` throws if the version exists. With merge, an equal ID deletes the current version and inserts the new one — [SqlDatasetDAO.java:121-143](/home/user/datacat/datacat-impl/src/main/java/org/srs/datacat/dao/sql/SqlDatasetDAO.java).
- **Locations.** `createDatasetLocation` asserts that the location can be created unless the check is skipped.
- **Status codes.** The comment above `handleFileAlreadyExists` states the intended protocol — [DatasetsResource.java:214-240](/home/user/datacat/rest/src/main/java/org/srs/datacat/rest/resources/DatasetsResource.java):
  - `POST` to a container, dataset exists and the representations conflict: 409.
  - Dataset exists but the version does not: 409 with the dataset URL in the `Location` header, so the client continues there.
  - Dataset and version exist but not all locations: 409 with the dataset-and-version URL.
  - Dataset exists and the representations do not conflict, with nothing more to add: 302 Found.
  - The same pattern one level down for a `POST` to a dataset (version) and to a version (locations).

So Datacat had the idea of an idempotent, conditional create: an equal entry is success (302), a different one is a conflict (409), and a partly existing one redirects the client to the level where it must continue. Its limits were one request per dataset, several round trips for a partly existing entry, no atomic batch, and no use of the standard HTTP preconditions (`If-Match`, `If-None-Match`, entity tags), which the earlier notes already record as absent.

> **Local context worth knowing.** The repository these notes live in is SLAC's *Datacat* — itself a science-side file catalog: Dataset → Versions → Locations (replicas), Folder/Group containers, typed user key:value metadata, a search query string compiled to SQL, a crawler for metadata extraction, AFS-style ACLs, Oracle/MySQL/HSQLDB backends, "foreign metadata" pseudo-tables (`/home/user/datacat/README.md`). ## 1. Science-side systems beyond iRODS/Rucio: data model, strengths, why they did not generalise

### Takeaway
Every science community has built a catalog whose *core* is the same three things (logical dataset identity, typed domain metadata, physical location) but each hard-wires one community's vocabulary (dimensions, proposals, runs, spatio-temporal items) or one transport/identity stack (Globus, git-annex, XRootD), and almost none exposes tables, schemas, lineage standards or a search-first UI. The most reusable ideas are Butler's registry/datastore split plus dimension model, MetaCat's JSON-metadata-in-Postgres plus MQL, and STAC's "small JSON core + extensions + static-or-API" spec.

### Cited Findings
**Workflow-/experiment-coupled catalogs (HEP, astronomy)**
- **Rubin/LSST Data Butler** (active; in production for LSST operations). Two components: a *Registry* that "works like a queryable database of available datasets" and a *Datastore* that serialises Python objects to storage and reads them back `[V]` — [Butler paper, arXiv:2206.14941](https://arxiv.org/abs/2206.14941). Data model `[BK]`: a configurable *dimension universe* (instrument, exposure, visit, detector, band, skymap/tract/patch…) forms a relational schema; a *DatasetType* = name + set of dimensions + storage class; a dataset is addressed by (dataset type, data ID, collection) and gets a UUID; *collections* come in RUN (immutable output of one processing run), TAGGED, CALIBRATION (validity-range lookup) and CHAINED (ordered search path) kinds; pipeline execution is planned as a *QuantumGraph* which doubles as provenance — [daf_butler docs](https://pipelines.lsst.io/modules/lsst.daf.butler/index.html). The delivered Butler has clients connect *directly* to the registry database (generally PostgreSQL; SQLite for testing), and Rubin has since had to build a REST "RemoteButler" for science users "for scaling and security reasons", with signed URLs for file access and at most very limited writes `[V]` — [DMTN-288](https://dmtn-288.lsst.io/DMTN-288.pdf), [DMTN-303](https://dmtn-303.lsst.io/v/DM-48071), [DMTN-242](https://dmtn-242.lsst.io/), [DMTN-283](https://dmtn-283.lsst.io/). A separate tech note exists purely on "Limiting Registry Access During Workflow Execution" `[V, title only]` — [DMTN-177](https://dmtn-177.lsst.io/). Good at: dimension-aware queries, calibration lookup, reproducible pipeline I/O. Did not generalise: Python-object/LSST-stack coupling, astronomy dimension universe, single-site registry with no replica concept (hence Rucio, §6).
- **DUNE MetaCat + Data Dispatcher** (Fermilab; active, DUNE production). File and dataset metadata catalog; objects identified by a `namespace:name` pair; required to work "on the scale of 100 million files and beyond"; designed generic "to be used by multiple experiments without changes"; MQL ("MEE-quel") selects files from datasets, combines queries with union/join/exclusion, supports named queries, parent/child provenance traversal, and filters backed by *external* metadata sources (e.g. a runs/conditions DB) via Python plug-ins "without copying them" `[V]` — [MetaCat CHEP 2021 paper](https://www.epj-conferences.org/10.1051/epjconf/202125102048), [MQL docs](https://fermitools.github.io/metacat/mql.html). Storage is PostgreSQL with file metadata as a JSON(B) document; MQL is compiled to SQL `[BK]` — [fermitools/metacat](https://github.com/fermitools/metacat). Replica location is deliberately *not* in MetaCat (Rucio does it); the Data Dispatcher hands files of a "project" to workers `[BK]` — [data_dispatcher docs](https://fermitools.github.io/data_dispatcher/). Did not generalise: no UI/discovery story beyond HEP, no schema registry for metadata, tiny developer base, tied to Fermilab auth and the Rucio pairing.
- **Fermilab SAM** (legacy, being replaced by MetaCat+Rucio+Data Dispatcher at DUNE). Monolith combining file metadata catalog, replica catalog, *dataset definitions as stored metadata queries* ("dimensions" language), and "projects" that track which consumer process received which file `[BK]` — [Illingworth 2014, J. Phys. Conf. Ser. 513 032045](https://doi.org/10.1088/1742-6596/513/3/032045). Good idea to keep: datasets-as-saved-queries and per-file delivery bookkeeping. Did not generalise: everything in one Oracle/Postgres-bound service, Fermilab-specific.
- **ATLAS AMI** (active, ATLAS-only). Dataset-level (not file-level) metadata catalog, dataset nomenclature, and "AMI-tags" that encode processing configuration; generic Java framework with its own metadata query language over SQL; pyAMI client `[BK]` — [AMI](https://ami.in2p3.fr/). Did not generalise: dataset granularity and ATLAS naming conventions are baked in.
- **CMS DBS** (active, CMS-only; server rewritten in Go as dbs2go). Relational bookkeeping of primary dataset / processed dataset / data tier → blocks → files → luminosity sections, with dataset and file parentage; replica locations live elsewhere (Rucio) `[BK]` — [dmwm/dbs2go](https://github.com/dmwm/dbs2go). Did not generalise: fixed schema, no user-defined metadata.
- **DIRAC File Catalog (DFC)** (active; LHCb, CTA, Belle II historically, ILC, many small VOs). One service that is both replica catalog and metadata catalog: hierarchical LFN namespace, user-defined typed metadata declared as indexes at directory or file level with inheritance down the tree, MySQL backend `[BK]` — [DIRAC docs](https://dirac.readthedocs.io/). Closest existing analogue to SLAC Datacat. Did not generalise: only usable inside the DIRAC framework and X.509/VOMS world.

**Federation / transport-centric**
- **Globus Search + Flows** (active, hosted SaaS, not open source). Search is a managed, Elasticsearch-like index of `subject` → entries with per-entry `visible_to` principals; published limits include 10 MB per document, 32 KB per field value, 1,000 distinct fields per index, 20 nesting levels, at most 10 entries per subject; changing a field type needs a full reindex done by Globus staff; Flows offers a hosted Search-ingest action provider; the "Searchable Files" guide is an extract-metadata-then-ingest pipeline with a replaceable extractor `[V]` — [Globus Search limits](https://docs.globus.org/api/search/limits/), [ingest](https://docs.globus.org/api/search/ingest/), [Searchable Files guide](https://docs.globus.org/api/search/guides/searchable_files/), [Flows Search-ingest AP](https://docs.globus.org/api/flows/hosted-action-providers/ap-search-ingest/). Good at: document-level ACL'd search with federated identity. Did not generalise as a catalog: no data model (bring your own JSON), no replicas/versions, proprietary service.
- **DataFed (ORNL)** (open source; research-lab scale; activity level not verified). Central metadata/orchestration service that is "not in the data path"; facilities attach locally-managed repositories and keep control of storage; raw transfer delegated to Globus/GridFTP; Globus identity required; not approved for sensitive data `[V]` — [DataFed overview](https://ornl.github.io/DataFed/system/overview.html), [arXiv:2004.03710](https://arxiv.org/abs/2004.03710). Records carry JSON metadata (optionally schema-validated), aliases, collections and provenance links; backend is a graph/document DB (ArangoDB) `[BK, uncertain — not confirmed by this session's search]` — [ORNL/DataFed](https://github.com/ORNL/DataFed). Did not generalise: hard Globus dependency, one managed copy per record (no replica model).
- **OSDF / Pelican** (active, NSF-funded, growing). Federation of six entity types — clients, object stores, origins, caches, a director and a registry; the director redirects HTTP GET/PUT to an origin/cache; the registry holds approved namespace prefixes each tied to a public key for token signing; origins/caches wrap an XRootD process; lineage goes back to the 2009 CMS XRootD federation, Pelican project started 2023 `[V]` — [Pelican overview (Rucio workshop 2024)](https://indico.cern.ch/event/1343110/contributions/6119455/attachments/2939390/5163600/Overview%20of%20the%20Pelican%20Platform.pdf), [OSDF docs](https://osg-htc.org/docs/data/osdf/overview/). It is a *delivery* network with a namespace, not a catalog: no metadata, no versions, no search.
- **Onedata** (Cyfronet; open source; EGI DataHub; activity not verified). Global POSIX-like virtual filesystem: *spaces* supported by one or more storage *providers*, coordinated by a zone service; per-file xattr/JSON/RDF metadata, QoS expressions that drive replication, CDMI/REST `[BK]` — [onedata.org](https://onedata.org/). Did not generalise: heavyweight to deploy, filesystem-first rather than catalog-first.
- **dCache (+ storage events)** (active; DESY/Fermilab/NDGF). Storage system with a Postgres-backed namespace (Chimera), tape integration and QoS classes; emits namespace/billing events to Kafka and offers client-subscribable storage events (SSE), which is the natural hook for event-driven cataloguing `[BK — not confirmed this session]` — [dCache](https://www.dcache.org/). It is a source of truth for one site's files, not a cross-site catalog.
- **DataLad / git-annex** (active; neuroscience-centred). Datasets are git repos; large-file content is content-addressed by git-annex with location tracking across "remotes"; datasets nest as subdatasets. Practical limits: "single datasets with 100k files" is where things get unwieldy, `save`/`status` can take minutes to hours with many tiny files; the 80 TB / 15 M-file HCP release was handled by ~1,200 subject-level subdatasets under a lean superdataset, with a RIA store holding only source-location information `[V]` — [DataLad Handbook: going big](https://handbook.datalad.org/en/latest/beyond_basics/101-160-gobig.html), [HCP use case](https://handbook.datalad.org/en/latest/usecases/HCP_dataset.html). Good at: decentralised, offline-capable versioning + provenance (`datalad run`). Did not generalise: no central query service, per-repo scaling ceiling.

**Facility (photon/neutron) catalogs**
- **SciCat** (active; PSI, ESS, MAX IV origin, "adopted by numerous research infrastructures"). Entities = MongoDB collections: Datasets (raw/derived), Proposals, Samples, Instruments, plus file listings and free-form `scientificMetadata`; backend TypeScript/NestJS on MongoDB, Angular frontend, containerised microservices `[V]` — [ICALEPCS 2023 paper](https://accelconf.web.cern.ch/icalepcs2023/papers/thmbcmo02.pdf), [ESS DMSC school](https://ess-dmsc-dram.github.io/dmsc-school/6-scicat/6-scicat.html). Good at: proposal/sample/instrument context, embargo-then-publish with DOIs. Did not generalise: facility-centric entity set; one location per dataset; weak typed queries over free-form metadata.
- **ICAT** (STFC; active but mature; ISIS, Diamond, ESRF and others). Strict relational schema Facility → Investigation → Dataset → Datafile with typed Parameters, Java EE server, separate ICAT Data Service for bytes, DataGateway UI `[BK]` — [icatproject.org](https://icatproject.org/). Did not generalise: rigid schema and Java EE stack.

**Spec-first and repository-style**
- **STAC + pystac / pgstac** (very active; de-facto standard in Earth observation). JSON spec: Catalog → Collection → Item (GeoJSON feature with datetime + geometry) → Assets (hrefs with roles/media types), extended via JSON-Schema extensions; works as static files or as an API `[BK]` — [stacspec.org](https://stacspec.org/). PgSTAC (schema + functions entirely inside Postgres) states it is "used in production to scale to hundreds of millions of STAC items"; Microsoft Planetary Computer is cited at 95 collections, 87 M items, 1.7 B assets; caveats: disable sort extension / use short timeouts beyond millions of records, result-count "context" is very expensive `[V]` — [pgstac README](https://github.com/stac-utils/pgstac/), [dev.to write-up](https://dev.to/kcarini/extending-postgis-with-timvttifeatures-and-pgstac-55nl), [stac-fastapi-pgstac](https://github.com/stac-utils/stac-fastapi-pgstac). Did not generalise beyond geo: mandatory spatio-temporal core; one href per asset (no replica semantics); no versioning in core.
- **Intake / intake-esm** (active, community-maintained). Intake: YAML catalogs mapping names to drivers that return dataframes/xarray; intake-esm: a CSV of asset paths + JSON descriptor of columns (the "ESM collection spec") used for CMIP6 `[BK]` — [intake](https://intake.readthedocs.io/), [intake-esm](https://intake-esm.readthedocs.io/). Shows that "a table of files with typed columns + a loader" is enough for many analysts. No service, ACLs, or write path.
- **CKAN, Dataverse, InvenioRDM (Zenodo)** (all active). Publication repositories: record = descriptive metadata + files + DOI/licence, deposit-and-freeze workflow, DataCite/DCAT export; InvenioRDM is Postgres + OpenSearch `[BK]` — [CKAN](https://ckan.org/), [Dataverse](https://dataverse.org/), [InvenioRDM](https://inveniordm.docs.cern.ch/). Harvard Dataverse now has an MCP implementation tied to Croissant `[V]` — [MLCommons Croissant 1.1](https://mlcommons.org/2026/02/croissant-1-1-standard/). Did not generalise to working data: per-record file counts are small, no replicas, no typed file-level queries.
- **NOMAD (+ Oasis)** (active; FAIRmat/NFDI). Uploads are parsed into entries whose processed "archive" follows the *Metainfo* schema language (Python or YAML schema packages, plugin-extensible); processed data stored as MessagePack with parts in MongoDB and Elasticsearch; an "Oasis" is a local deployment `[V]` — [NOMAD data docs](https://docs.nomad-lab.eu/explanation/data.html), [schema packages](https://nomad-lab.eu/prod/v1/docs/howto/customization/plugins_dev.html). Good at: parser-driven automatic metadata extraction and a typed, extensible schema language. Did not generalise: materials-specific parsers/schemas, upload-centric (bytes must come to NOMAD).
- **Materials Commons** (U. Michigan/PRISMS; small; health not verified). Project → experiments → samples/processes/files graph for materials workflows `[BK]` — [materialscommons.org](https://materialscommons.org/).

### Inferences
- The recurring split is **(a) logical catalog with typed metadata, (b) replica/location service, (c) delivery/transfer layer, (d) workflow bookkeeping**. Systems that fused all four (SAM, DFC, iRODS for contrast) proved hard to adopt piecemeal; systems that did only one (MetaCat, Pelican, STAC) spread further but force integrators to glue. A new system should own (a)+(b) cleanly and treat (c)/(d) as plug-ins.
- Non-generalisation causes cluster into five: hard-wired domain vocabulary; coupling to one auth/transport stack (X.509, Globus, XRootD); direct-DB clients (Butler) or framework lock-in (DIRAC); no discovery UI; and bus-factor (one lab's team).
- Butler's dimension model and MetaCat's "external metadata as query-time join" (also Datacat's "foreign metadata") are three independent arrivals at the same need: **joining file metadata against small relational reference tables (runs, exposures, calibrations)**. This is a first-class requirement, not an edge case.

### Gaps
- Could not open the Butler, MetaCat or Rubin data-movement papers in full (arxiv.org / lss.fnal.gov blocked): Butler collection semantics, MetaCat's exact Postgres schema/indexing and any benchmark numbers are from background knowledge, not verified.
- Project health in late 2026 not verified for: Onedata, DataFed, Materials Commons, ICAT, AMI, SAM retirement status, DIRAC DFC user base. dCache storage-event details not confirmed (search returned nothing).
- DataFed's database (ArangoDB) not confirmed by search.

## 2. Data-science-side systems beyond Amundsen/DataHub, and how they treat non-tabular "filesets/volumes"

### Takeaway
By 2026 the lakehouse world has converged on a REST catalog of `catalog.schema.object` with credential vending, and has grown "volume/fileset/model" object kinds — but every one of them treats a fileset as an **opaque governed path prefix**: no per-file records, checksums, versions, replicas or typed per-file metadata. Per-file versioning exists only in the git-like tools (lakeFS, DVC, Hugging Face Hub), which in turn have no replica/site model.

### Cited Findings
- **Iceberg REST catalog spec** (very active; the de-facto interop API). Iceberg 1.11 added *remote scan planning* (the catalog plans the scan and streams file-scan tasks, clients no longer read manifests), storage credentials returned in planning responses, and *remote signing* (catalog pre-signs each file access, engine holds no token); a `referenced-by` field tracks dependent views; table-spec v3 reached GA across major platforms in H1 2026, v4 is still being defined; a "catalog-only planning" mode was still being debated on the dev list `[V]` — [Iceberg 1.11.0 release](https://iceberg.apache.org/blog/apache-iceberg-1.11.0-release/), [Snowflake on 1.11](https://www.snowflake.com/en/blog/engineering/apache-iceberg-1-11-new-features-fixes/), [State of Iceberg catalogs, June 2026](https://amdatalakehouse.substack.com/p/the-state-of-apache-iceberg-catalogs), [REST catalog docs](https://iceberg.apache.org/docs/nightly/rest-catalog/). A Google Open Source post (Oct 2026) concerns standardising fine-grained access control in the REST catalog `[V, title only]` — [Google OSS blog](https://opensource.googleblog.com/2026/10/standardizing-fine-grained-access-control-in-apache-icebergs-rest-catalog.html). The spec covers namespaces, tables and views only — no file/volume object.
- **Apache Polaris** (very active). Graduated to ASF top-level project in February 2026 (sources give 15, 18 or 19 Feb; ASF press release 5 Mar 2026); monthly releases (1.4.0 on 23 Apr 2026, 1.6.0 on 8 Jul 2026) `[V]` — [ASF incubator page](https://incubator.apache.org/projects/polaris.html), [board minutes](https://whimsy.apache.org/board/minutes/Polaris.html), [ASF announcement](https://news.apache.org/foundation/entry/the-apache-software-foundation-graduates-two-open-source-projects-from-incubator). "Generic tables" (Delta, Hudi and other non-Iceberg formats in the same namespaces) reportedly went GA `[V, secondary source]` — [State of Polaris, July 2026](https://dev.to/alexmercedcoder/the-state-of-apache-polaris-in-july-2026-from-incubating-catalog-to-the-governance-layer-of-the-1n3h). Lance publishes a namespace mapping onto Polaris `[V]` — [lance-namespace](https://github.com/lance-format/lance-namespace). No fileset/volume object found.
- **Unity Catalog OSS** (LF AI & Data; Apache-2.0; active but trails the Databricks product). v0.1 (June 2024) covered tables, volumes and AI functions; 0.3.x added a client module and auth work; the roadmap lists temporary-credential vending for volumes and for models `[V]` — [Databricks announcement](https://www.databricks.com/blog/open-sourcing-unity-catalog), [unitycatalog repo](https://github.com/unitycatalog/unitycatalog). Volume semantics (from the Databricks product docs): volumes "govern non-tabular data of any format", are "intended for path-based data access only", cannot be table locations, and external engines (Daft, DuckDB, Ray) reach them through credential vending that inherits the principal's privileges `[V]` — [Databricks volumes docs](https://docs.databricks.com/aws/en/volumes/), [community blog](https://community.databricks.com/t5/technical-blog/processing-unstructured-data-in-volumes-with-unity-catalog-open/ba-p/153360). Registered models/model versions exist in OSS UC as an MLflow registry backend `[BK]` — [unitycatalog repo](https://github.com/unitycatalog/unitycatalog).
- **Apache Gravitino** (very active; 1.0.0 in 2025, 1.1.0, latest seen 1.3.1; served from gravitino.apache.org, i.e. apparently graduated — date not verified). "Catalog of catalogs" (metalake → catalog → schema → object). *Fileset*: for "non-tabular data like training datasets and other raw data"; 1.0 renamed the Hadoop catalog to "fileset catalog" and added `create_multiple_location_fileset` (multiple *named* storage locations per fileset); "currently only supports managing Hadoop Compatible File System (HCFS) locations"; 1.1 manages filesets across multiple HDFS clusters. *Model catalog* (since 0.9): `catalog.schema.model` with versions, later multiple storage locations per model version `[V]` — [Gravitino 1.0.0 release notes](https://gravitino.apache.org/blog/gravitino-1-0-0-release-notes), [fileset docs](https://gravitino.apache.org/docs/next/fileset-catalog), [model catalog docs](https://gravitino.apache.org/docs/next/model-catalog), [1.1.0 notes](https://gravitino.apache.org/blog/gravitino-1-1-0-release-notes). Access is through a virtual filesystem (`gvfs://fileset/catalog/schema/fileset/path`) with Java (HCFS) and Python (fsspec) clients and credential vending `[BK]` — [GVFS docs](https://gravitino.apache.org/docs/next/how-to-use-gvfs). **Closest lakehouse-side feature to a science replica model**, but locations are named alternatives of a directory, not tracked per-file replicas with state/checksum.
- **OpenMetadata** (very active; v1.x → 2.0 docs exist). MySQL or Postgres as the metadata store, Elasticsearch/OpenSearch as search index; entity change events are stored in the server DB and indexed into the search engine; ingestion orchestrated with Airflow; third-party description: relational storage "avoiding the complexity of graph databases" `[V]` — [OpenMetadata architecture docs](https://docs.open-metadata.org/developers/architecture), [HackerNoon](https://www.hackernoon.com/what-the-heck-is-open-metadata). Entities are defined as JSON Schemas; object stores are modelled as a "Container" entity (bucket/prefix with optional file-format/schema) `[BK]` — [OpenMetadata](https://github.com/open-metadata/OpenMetadata). Ships a native MCP server (reported since v1.8.0) with OAuth/PKCE so tools run with the calling user's permissions `[V, partly vendor-sourced]` — [open-metadata.org llms.txt](https://open-metadata.org/llms.txt). Absence of Kafka as a hard dependency was *not* confirmed by this session's search.
- **Project Nessie** (status uncertain). Git-like catalog: branches/tags/commits across many Iceberg tables, multi-table transactions. Dremio announced in 2024 that Nessie's capabilities would be contributed to Polaris "at which time Project Nessie will be retired"; a Dremio post covers migrating Nessie → Polaris without rewriting data `[V]` — [Nessie blog, Aug 2024](https://projectnessie.org/blog/2024/08/02/open-source-polaris-announcement/), [Datanami](https://www.datanami.com/2024/07/30/polaris-catalog-to-be-merged-with-nessie-now-available-on-github), [Dremio migration post](https://www.dremio.com/blog/migrating-from-nessie-to-apache-polaris-without-rewriting-iceberg-data/). Whether catalog-level branching has actually landed in Polaris was not confirmed.
- **lakeFS** (active). Git-like repositories/branches/commits over any object-store prefix, format-agnostic, so it versions arbitrary files; S3-compatible gateway `[BK]` — [lakeFS docs](https://docs.lakefs.io/). Acquired the **DVC** open-source project from Iterative on 18 Nov 2025; DVC stays a separate Apache-licensed project `[V]` — [lakeFS acquires DVC](https://lakefs.io/blog/lakefs-acquires-dvc/), [DVC FAQ](https://dvc.org/blog/dvc-joins-lakefs-your-questions-answered/). **DVC**: `.dvc` pointer files with content hashes in git, content-addressed cache, pluggable remotes, `dvc.yaml` pipelines `[BK]` — [dvc.org](https://dvc.org/doc).
- **Lance / LanceDB namespaces** (active). The Lance Namespace spec standardises access to collections of Lance tables with two flavours: a *directory* namespace ("storage-only… no external metadata service") and a *REST* namespace (OpenAPI), plus mappings onto Polaris, Unity Catalog, Hive Metastore and Iceberg REST `[V]` — [LanceDB namespaces docs](https://docs.lancedb.com/namespaces), [lance-namespace spec](https://lancedb.github.io/lance-namespace). Lance tables hold blobs/embeddings inline, so "non-tabular" data becomes rows rather than files.
- **Hugging Face Hub** (dominant ML dataset/model hub). Repos are git-based (versioned); storage migrated from Git LFS to *Xet* — content-defined chunking (GearHash, ~64 KB target, 8–128 KB range), chunk-level dedup across files and repos; an IETF Internet-Draft specifies the protocol (default suite BLAKE3 + Gearhash + LZ4; rev -04/-05 June 2026); Parquet content-defined chunking in PyArrow/pandas makes Parquet dedupe well; *Storage Buckets* (10 Mar 2026) add mutable S3-like object storage next to versioned repos `[V]` — [Xet docs](https://huggingface.co/docs/hub/xet), [IETF draft-denis-xet](https://datatracker.ietf.org/doc/html/draft-denis-xet-04), [Parquet CDC](https://huggingface.co/blog/parquet-cdc), [Storage Buckets](https://huggingface.co/blog/storage-buckets). Dataset cards + auto-generated Croissant JSON-LD: 700K+ datasets (MLCommons) / 800K+ on HF alone (ODI) carry Croissant `[V, figures conflict]` — [MLCommons](https://mlcommons.org/2026/02/croissant-1-1-standard/), [ODI](https://theodi.org/news-and-events/blog/croissant-11/).
- **MLflow** (very active; MLflow 3 in 2025). Experiments → runs with params/metrics/artifacts; model registry with versions and aliases; `mlflow.data` records dataset name/digest/source/schema per run `[BK]` — [mlflow.org docs](https://mlflow.org/docs/latest/). Artifacts are opaque files under an artifact root: no metadata queries over them.
- **Delta Sharing** (active open protocol). REST: share → schema → table; server returns short-lived pre-signed URLs to Parquet files; open spec is table-centric `[BK]` — [delta-io/delta-sharing protocol](https://github.com/delta-io/delta-sharing/blob/main/PROTOCOL.md).
- **Marquez** (LF AI & Data *graduated*; reference implementation of the OpenLineage API; no 2026 Marquez release found in this session's search) `[V]` — [OpenLineage repo](https://github.com/OpenLineage/OpenLineage), [LF AI & Data](https://lfaidata.foundation/?p=5356). Single Postgres backend; model = namespaces, datasets (with versions), jobs, runs `[BK]` — [MarquezProject/marquez](https://github.com/MarquezProject/marquez).

**Which handle non-tabular filesets, and how (summary)**

| System | Non-tabular object | Granularity tracked | Versions | Multiple locations | Per-file metadata/checksum |
|---|---|---|---|---|---|

| Gravitino | Fileset | directory; named locations | no | yes (named alternatives, HCFS only) | no |
| OpenMetadata | Container | bucket/prefix (+ inferred schema) | no | no | no |
| Polaris / Iceberg REST | none (generic tables only) | — | — | — | — |
| lakeFS / DVC | any object | per object | yes (commits) | DVC remotes (no state tracking) | hash only |
| HF Hub | repo files / buckets | per file, chunk-dedup | yes (git) for repos | no | hash; card + Croissant at dataset level |
| MLflow | run artifacts | per file | by run | no | no |
| Lance | rows with blob columns | per row | table versions | no | columns |

(Table synthesises the cited findings above; UC/Gravitino rows `[V]`, others `[BK]`.)

### Inferences
- "Volume/fileset" in lakehouse catalogs is a **governance handle** (who may get credentials for this prefix), not a **catalog of files**. A science catalog needs the opposite emphasis. A unified system can present each science dataset/container *as* a fileset/volume to lakehouse tools (path-prefix + credential vending) while holding the per-file truth itself.
- The lakehouse side is consolidating fast around Iceberg REST + Polaris/UC/Gravitino/Lakekeeper; a new catalog should **not** compete as a table catalog. It should federate to or embed an Iceberg REST endpoint and spend its novelty budget on files, replicas and typed metadata.
- Gravitino's "multiple named locations" and model-version "multiple storage locations" show demand for location plurality arriving from the ML side — evidence that replica-awareness is not purely a HEP concern.

### Gaps
- Unity Catalog OSS release-by-release status of volumes/models/credential vending in 2026 not verified (search surfaced only 0.1 and 0.3.1 notes and a roadmap copy).
- Nessie's 2026 status (retired? merged?) unresolved. Polaris generic-tables GA is from a secondary blog.
- Gravitino's GVFS/fsspec details, ASF graduation date and whether any release added per-file tracking could not be checked (site blocked).
- Did not research Lakekeeper, DuckLake, Apache Atlas, Egeria, Kedro/Feast/feature stores in depth.

## 3. Standards to adopt rather than reinvent

### Takeaway
There is a usable standard for almost every *edge* of the system (lineage events, dataset description, packaging, PIDs, table catalog API, auth tokens, events, agent access) but **no standard for the core** — a logical file with versions, checksummed replicas across sites and typed metadata. The right posture is: own a small core model, and make every external surface a standard projection of it.

### Cited Findings
**Lineage / provenance**
- **OpenLineage** — graduated LF AI & Data project (graduation dated 20 Sep 2023); actively released (Airflow provider 2.20.1 dated 23 Aug 2026) `[V]` — [OpenLineage docs](https://openlineage.io/docs/), [Airflow provider changelog](https://airflow.apache.org/docs/apache-airflow-providers-openlineage/stable/changelog.html). Model: Run/Job/Dataset events with extensible *facets*; datasets are named by `namespace` (e.g. `s3://bucket`, `postgres://host:port`) + `name` (path or `db.schema.table`); facets exist for schema, column-level lineage, data-quality metrics, dataset version, storage format and symlinks (alternative identifiers) `[BK]` — [OpenLineage naming spec](https://openlineage.io/docs/spec/naming/). Use as the push-ingest wire format for lineage; the *symlinks* facet is the hook for mapping physical URLs to logical catalog IDs.
- **W3C PROV (PROV-O/PROV-DM)** — Entity/Activity/Agent; W3C Recommendation 2013 `[BK]` — [PROV-O](https://www.w3.org/TR/prov-o/). Croissant 1.1 adopted PROV-O for dataset chain-of-custody `[V]` — [ODI on Croissant 1.1](https://theodi.org/news-and-events/blog/croissant-11/). Use as the *export/archival* vocabulary; OpenLineage as the operational one.

**Dataset description, packaging, identifiers**
- **MLCommons Croissant 1.1** (Feb 2026) — JSON-LD on top of schema.org/Dataset describing resources (FileObject/FileSet) and RecordSets; 1.1 adds PROV-O provenance and is positioned as "agent-ready"; embedded by Hugging Face, Kaggle, OpenML; adopted by Common Crawl; MCP implementations exist for Harvard Dataverse and Kaggle `[V]` — [MLCommons Croissant 1.1](https://mlcommons.org/2026/02/croissant-1-1-standard/), [Croissant paper](https://arxiv.org/abs/2403.19546).
- **schema.org/Dataset** and **DCAT 3** (W3C Recommendation, 2024; adds dataset series and versioning properties) for web discovery and harvesting `[BK]` — [schema.org/Dataset](https://schema.org/Dataset), [DCAT 3](https://www.w3.org/TR/vocab-dcat-3/).
- **RO-Crate** — JSON-LD packaging of files + contextual metadata, with profiles such as Workflow Run Crate for provenance `[BK]` — [researchobject.org/ro-crate](https://www.researchobject.org/ro-crate/).
- **DataCite metadata schema / DOIs** for citation; **FAIR principles** (Wilkinson et al. 2016) and **FAIR Digital Objects** (PID + typed kernel metadata record) as the framing funders expect `[BK]` — [DataCite schema](https://schema.datacite.org/), [FAIR principles](https://doi.org/10.1038/sdata.2016.18), [FDO Forum](https://fairdo.org/).
- **STAC** for anything spatio-temporal — also a good *design template* (tiny core, JSON-Schema extensions, static-or-API) `[BK]` — [stacspec.org](https://stacspec.org/).
- **IVOA**: TAP (ADQL queries over tables), ObsCore (common observation metadata table), DataLink (links from a record to files/services/cutouts), plus VOSpace/SIA `[BK]` — [IVOA documents](https://www.ivoa.net/documents/). SKA's SRCNet work adapts Rucio "for astronomical metadata via a metadata plugin that enables discovery with existing astronomical client libraries" `[V]` — [SKAO Rucio workshop 2024](https://indico.cern.ch/event/1343110/contributions/6089547/attachments/2937876/5160662/JSC%20-%20DDM%20Assessment%20-%20Rucio%20Workshop%2030-09-24%20(1).pdf).

**Tables / lakehouse**
- **Iceberg REST catalog** (OpenAPI) incl. credential vending, remote signing, remote scan planning — see §2 `[V]` — [Iceberg REST docs](https://iceberg.apache.org/docs/nightly/rest-catalog/). **Delta Sharing** for cross-org table sharing `[BK]` — [protocol](https://github.com/delta-io/delta-sharing/blob/main/PROTOCOL.md).

**Storage addressing and integrity**
- **fsspec** URL conventions (`s3://`, `gs://`, `abfs://`, `root://`, `https://`, chained `simplecache::s3://…`) are what Python data tools expect; Gravitino and HF both expose fsspec filesystems (`gvfs://`, `hf://`) `[BK; hf:// seen in V source]` — [fsspec docs](https://filesystem-spec.readthedocs.io/), [HF Parquet CDC post](https://huggingface.co/blog/parquet-cdc).
- **Checksums are plural and site-dependent.** At Rubin, checksum computation at registration time is flagged as a bottleneck; the French and UK facilities store adler32 at file-creation time, USDF does not `[V]` — [Rubin multi-site data movement, SA3CC 2026](https://www.amlight.net/wp-content/uploads/2026/01/SA3CC2026_-Rubin-Multi-site-Data-Movement-Wei-Yang.pdf). adler32 is the WLCG/XRootD norm, md5/sha256 the repository norm, crc32c the cloud-object-store norm; RFC 9530 `Content-Digest`/`Repr-Digest` is the HTTP-level standard `[BK]` — [RFC 9530](https://www.rfc-editor.org/rfc/rfc9530). Content-defined chunk hashing is now being standardised (XET Internet-Draft) `[V]` — [draft-denis-xet](https://datatracker.ietf.org/doc/html/draft-denis-xet-04).

**AuthN / AuthZ**
- **OIDC + WLCG tokens / SciTokens** — capability JWTs with scopes like `storage.read:/path`. The X.509→token transition has slipped: the 2022 plan targeted March 2026 for users no longer needing certificates; a Sept 2025 WLCG deck lists CMS token-only jobs in 2026-Q3, Data Challenge 2027 in 2027-Q1 and X.509/VOMS phase-out in 2028-Q1; "most experiments are still using x.509 for storage auth" `[V]` — [WLCG token progress, Sept 2025](https://indico.cern.ch/event/1566166/contributions/6688798/attachments/3141551/5576025/WLCG_Token_Progress-250924.pdf), [CHEP 2024 paper](https://www.epj-conferences.org/10.1051/epjconf/202533701179), [WLCG AuthZ WG note](https://indico.cern.ch/event/1550581/note/). Pelican ties each namespace prefix to a signing key in its registry `[V]` — [Pelican overview](https://indico.cern.ch/event/1343110/contributions/6119455/attachments/2939390/5163600/Overview%20of%20the%20Pelican%20Platform.pdf).
- **Zanzibar-style ReBAC (OpenFGA, SpiceDB)** and **Cedar** (policy language with ABAC/RBAC, formally analysable) are the two open families for fine-grained authorization `[BK]` — [OpenFGA](https://openfga.dev/), [Cedar](https://www.cedarpolicy.com/). Lakehouse precedent: vended credentials "inherit the… privileges of the requesting principal" and are scoped to a table's/volume's storage prefix `[V]` — [Databricks community blog](https://community.databricks.com/t5/technical-blog/processing-unstructured-data-in-volumes-with-unity-catalog-open/ba-p/153360), [State of Iceberg catalogs](https://amdatalakehouse.substack.com/p/the-state-of-apache-iceberg-catalogs).

**Events, schemas, agents**
- **CloudEvents** (CNCF graduated) as the envelope for catalog change events and storage notifications `[BK]` — [cloudevents.io](https://cloudevents.io/).
- **JSON Schema (2020-12)** for validating user metadata; **LinkML** as a higher-level modelling language that generates JSON Schema, SQL DDL, Pydantic and RDF from one definition `[BK]` — [json-schema.org](https://json-schema.org/), [linkml.io](https://linkml.io/). Precedents: OpenMetadata defines all entities in JSON Schema `[BK]` — [OpenMetadata](https://github.com/open-metadata/OpenMetadata); NOMAD's Metainfo is a bespoke equivalent `[V]` — [NOMAD docs](https://docs.nomad-lab.eu/explanation/data.html).
- **Model Context Protocol (MCP)** — now table stakes for catalogs: DataHub ships an MCP server (PyPI `mcp-server-datahub`) with optional semantic search; OpenMetadata has a native MCP server; Google's Knowledge Catalog offers a remote MCP server; Informatica's Catalog Discovery MCP server was in private preview as of July 2026; Dataverse and Kaggle have Croissant-based MCP implementations `[V]` — [mcp-server-datahub](https://pypi.org/project/mcp-server-datahub/), [Google Knowledge Catalog for AI agents](https://docs.cloud.google.com/dataplex/docs/ai-overview), [Informatica](https://onlinehelp.informatica.com/IICS/prod/agentic-ui/en/cc-aiae-gs-mcp-servers/Catalog_Discovery.html), [MLCommons](https://mlcommons.org/2026/02/croissant-1-1-standard/). Spec: [modelcontextprotocol.io](https://modelcontextprotocol.io/) `[BK]`.

### Inferences
- Suggested mapping (designer's cheat-sheet): identity/PIDs → internal stable ID + optional DOI (DataCite); dataset description out → Croissant + schema.org + DCAT (one JSON-LD generator covers all three); package export → RO-Crate; lineage in → OpenLineage, lineage out → PROV; tables → *be or front* an Iceberg REST catalog; astronomy/EO facades → TAP/ObsCore/DataLink and STAC as optional read-only projections; access → OIDC with pluggable token profiles (WLCG/SciTokens scopes map naturally to path-prefix capabilities) + a ReBAC/Cedar policy engine; change feed → CloudEvents; metadata schemas → JSON Schema authored via LinkML; agents → MCP server executing with the caller's identity.
- Because checksum algorithms differ by site and recomputation is a measured bottleneck, the core model should store **a set of (algorithm, value) per file version**, accept whatever the storage already has, and backfill others lazily.
- The WLCG token slip (2026 → 2028) means a science-grade catalog must support **both** X.509/VOMS-fronted storage and tokens for several more years; do not design auth around tokens only.
- OpenLineage's `namespace+name` for files is a *physical* identifier; a replica-aware catalog needs the symlinks facet (or a resolver) to collapse N physical URLs to one logical dataset, otherwise lineage graphs fragment per site.

### Gaps
- OpenLineage spec details (naming, facets) not re-verified (site blocked). RO-Crate current version, DataCite schema version, FDO specification maturity, OpenFGA/Cedar foundation status in 2026 not checked.
- No evidence gathered on real-world adoption of Cedar/OpenFGA *inside* open-source data catalogs, or of LinkML in catalog products.
- No standard found (or known) for replica/location description across sites — this is a genuine gap, not just an unsearched one; treat as uncertain.

## 4. Requirements gap analysis: scientists vs data scientists

### Takeaway
The two communities' requirements are nearly disjoint at the *file vs. column* boundary: science catalogs know everything about where immutable files are and nothing about what is inside them or who uses them; enterprise catalogs know schemas, lineage and popularity but stop at "a path prefix". Evidence from recent science projects shows the pain is exactly at this seam (two catalogs kept in sync by message bus).

### Cited Findings
**What scientists need that enterprise/lakehouse catalogs lack (with evidence)**
- *Replica/site awareness.* Rubin runs Rucio for "file metadata and location tracking" alongside Butler for dataset search; each site is one or more Rucio storage elements with its own local Butler registry `[V]` — [Rubin multi-site movement 2026](https://www.amlight.net/wp-content/uploads/2026/01/SA3CC2026_-Rubin-Multi-site-Data-Movement-Wei-Yang.pdf), [DMTN-198 / data backbone docs](https://dmtn-198.lsst.io/). Lakehouse equivalents stop at a governed prefix (UC volumes: "path-based data access only") or named alternative locations (Gravitino) `[V]` — [UC volumes](https://docs.databricks.com/aws/en/volumes/), [Gravitino 1.0 notes](https://gravitino.apache.org/blog/gravitino-1-0-0-release-notes).
- *Scale in file count.* MetaCat's stated design point is 100 M files "and beyond"; Planetary Computer's STAC holds 87 M items / 1.7 B assets on Postgres `[V]` — [MetaCat paper](https://www.epj-conferences.org/10.1051/epjconf/202125102048), [pgstac write-up](https://dev.to/kcarini/extending-postgis-with-timvttifeatures-and-pgstac-55nl). Git-style tools degrade around 100k files per repository `[V]` — [DataLad handbook](https://handbook.datalad.org/en/latest/beyond_basics/101-160-gobig.html). Hosted search indexes cap at 1,000 distinct fields `[V]` — [Globus Search limits](https://docs.globus.org/api/search/limits/).
- *Typed metadata queries over huge file sets, joined with reference data.* MQL with external-source filters (runs DB) `[V]` — [MQL docs](https://fermitools.github.io/metacat/mql.html); SLAC Datacat's `run > 6200 and runQuality =~ "GO*"` over container patterns and its "foreign metadata" pseudo-tables — `/home/user/datacat/README.md`; Butler's dimension records `[BK]` — [daf_butler docs](https://pipelines.lsst.io/modules/lsst.daf.butler/index.html).
- *Versioned immutable files and run-style collections* (Butler RUN collections; Datacat dataset versions) — sources as above.
- *Embargo / proprietary periods and collaboration ACLs.* SKA's SRCNet work explicitly covers "adapting Rucio's metadata handling and embargo control" (May 2026 talk) `[V]` — [SRCNet talk, May 2026](https://indico.cern.ch/event/1471803/contributions/6967407/); Globus Search entries carry `visible_to` principals `[V]` — [Globus ingest](https://docs.globus.org/api/search/ingest/); SciCat/ICAT are organised around proposals/investigations `[V/BK]` — [SciCat ICALEPCS 2023](https://accelconf.web.cern.ch/icalepcs2023/papers/thmbcmo02.pdf).
- *Integrity at registration, heterogeneous checksums* — Rubin checksum bottleneck `[V]` — [SA3CC 2026 slides](https://www.amlight.net/wp-content/uploads/2026/01/SA3CC2026_-Rubin-Multi-site-Data-Movement-Wei-Yang.pdf).
- *Heterogeneous auth across sites* (X.509 until ~2028 alongside tokens) `[V]` — [WLCG token progress](https://indico.cern.ch/event/1566166/contributions/6688798/attachments/3141551/5576025/WLCG_Token_Progress-250924.pdf).
- *Offline / HPC / batch access without a round-trip per file*: Rubin wrote a tech note on limiting registry access during workflow execution `[V, title]` — [DMTN-177](https://dmtn-177.lsst.io/); DataLad's value is offline operation `[V]` — [arXiv:2505.06558](https://arxiv.org/abs/2505.06558).
- *Online/time-critical paths are a different regime*: SKA's assessment found Rucio "not suited to online or time-critical workflows" and large-scale metadata "still needed testing" `[V]` — [ESCAPE DIOS deployment experience 2022](https://indico.in2p3.fr/event/26307/contributions/105835/attachments/69440/98054/ESCAPE%20DIOS%20Workshop,%20Deployment%20Experience,%20March%202022.pdf).
- *Citations/DOIs and long-term preservation* are handled by a separate tier (Zenodo/InvenioRDM, Dataverse, SciCat publication) `[BK]` — [InvenioRDM](https://inveniordm.docs.cern.ch/).

**What data scientists need that science catalogs lack (with evidence)**
- *Schema/column metadata, lineage, quality, usage* are the core entities of OpenMetadata/Marquez/OpenLineage `[V/BK]` — [OpenMetadata architecture](https://docs.open-metadata.org/developers/architecture), [OpenLineage](https://openlineage.io/docs/). None of Butler, MetaCat, DFC, SciCat, ICAT expose column schemas or OpenLineage (no evidence found; see Gaps).
- *Search-first discovery, increasingly semantic and agent-driven*: DataHub OSS embeds documents for semantic search from v1.4.0; OpenMetadata MCP offers search-by-meaning `[V]` — [DataHub MCP server](https://pypi.org/project/mcp-server-datahub/), [open-metadata.org](https://open-metadata.org/llms.txt).
- *Dataframe/notebook access by name, with credentials handled for them*: UC credential vending to Daft/DuckDB/Ray; `hf://` paths in pandas/PyArrow; Gravitino GVFS `[V]` — [Databricks community blog](https://community.databricks.com/t5/technical-blog/processing-unstructured-data-in-volumes-with-unity-catalog-open/ba-p/153360), [HF Parquet CDC](https://huggingface.co/blog/parquet-cdc).
- *ML dataset and model versioning / registry*: HF repos, DVC/lakeFS, MLflow registry, UC and Gravitino model catalogs (see §2).
- *Self-describing datasets for loaders and agents*: Croissant on 700K–800K+ datasets `[V]` — [MLCommons](https://mlcommons.org/2026/02/croissant-1-1-standard/).
- *Governance* (fine-grained access control standardised at the catalog API) `[V, title]` — [Google OSS blog, Oct 2026](https://opensource.googleblog.com/2026/10/standardizing-fine-grained-access-control-in-apache-icebergs-rest-catalog.html).

### Inferences
- **Side-by-side requirement matrix (synthesis):**

| Capability | Science catalogs | Enterprise/lakehouse catalogs | Unified system must |
|---|---|---|---|
| Unit of record | logical file / dataset of files | table / column / prefix | model both; a file-set can *have* a schema, a table can *have* files |
| Location | N replicas with state, site, QoS/tape | one path (or named alternates) | per-file replica records + prefix-level "volume" view |
| Mutability | immutable versions, run collections | mutable tables with snapshots | immutable file versions + snapshot/branch semantics for collections |
| Metadata | user-defined typed key/values, dimensions, 10^8–10^10 rows | fixed entity schemas, tags, glossary | schema-registered typed metadata, indexed, joinable to reference tables |
| Query | predicate language → file lists | keyword/semantic search → asset pages | both, over the same store |
| Lineage | parentage of files (parent/child) | job/run/column lineage (OpenLineage) | ingest OpenLineage; store file-level parentage compactly |
| Access control | VO/collaboration groups, embargo dates, capability tokens | RBAC/ABAC, credential vending, masking | group + time-based embargo + vended/presigned access |
| Ingestion | bulk registration by workflows, crawlers | pull connectors, push events | bulk API first; crawlers/extractors; OpenLineage push |
| Access path | batch jobs, HPC, xrootd/https, offline manifests | notebooks, dataframes, fsspec, SQL engines | fsspec + Iceberg REST + exportable manifests |
| Preservation | DOIs, long-term, tape | retention policies | DOI minting + RO-Crate/Croissant export; tape as a replica QoS state |

- The 10^8–10^10 range matters architecturally: 10^8 is demonstrated on a single well-tuned Postgres (MetaCat target, pgstac); 10^10 is beyond any cited single-node deployment and needs partitioning/sharding by scope from day one, or a design in which bulk per-file rows can live in columnar files (Parquet/Iceberg) with only hot/indexed subsets in the OLTP store. This is an inference; no source in this session demonstrates 10^10 file records in one catalog.
- Usage/popularity signals are absent from science catalogs yet are the cheapest relevance feature for search; access-trace events (Rucio-style traces, storage events) can feed them.
- Scientists' "dimensions" and data scientists' "partitions" are the same idea; expose dimension values as partition-like columns so a metadata query result can be read as a table of files (the intake-esm pattern).

### Gaps
- No user-survey or requirements document comparing the two communities was found; the matrix is synthesis from system capabilities, not from stated user research.
- Negative claims ("science catalogs lack OpenLineage/column metadata") rest on absence of evidence in this session, not on a systematic check.
- No verified numbers for tape/QoS requirements or for bulk-registration throughput targets (files/s) in any system outside the separately-researched Rucio.

## 5. Architecture patterns and pitfalls (with evidence)

### Takeaway
The evidence favours a **Postgres-first, single-service core with an API in front (never direct DB clients), JSON(B) typed metadata, a query language compiled to SQL, an outbox/change-feed driving optional search and vector indexes, and a strict catalog/datastore separation with credential vending** — deployable as one binary with an embedded-DB mode. The heavy Kafka + Elasticsearch + graph-DB stack is the exception among successful 2024–2026 catalogs, not the rule.

### Cited Findings
**Postgres-first vs. multi-store stacks**
- Postgres (or MySQL) as sole source of truth: Butler registry (PostgreSQL; SQLite for tests) `[V]` — [DMTN-288](https://dmtn-288.lsst.io/DMTN-288.pdf); pgstac at "hundreds of millions" of items, logic implemented as SQL functions `[V]` — [pgstac](https://github.com/stac-utils/pgstac/); OpenMetadata (MySQL/Postgres + a search index, no graph DB) `[V]` — [OpenMetadata docs](https://docs.open-metadata.org/developers/architecture); MetaCat and Marquez (Postgres only) `[BK]` — [metacat](https://github.com/fermitools/metacat), [marquez](https://github.com/MarquezProject/marquez).
- Document/multi-store designs in science: SciCat on MongoDB (chosen for flexible format) `[V]` — [SciCat ICALEPCS 2023](https://accelconf.web.cern.ch/icalepcs2023/papers/thmbcmo02.pdf); NOMAD on MessagePack files + MongoDB + Elasticsearch `[V]` — [NOMAD docs](https://docs.nomad-lab.eu/explanation/data.html). Globus Search shows the operational cost of search-engine-as-store: field-type changes need a full reindex, 1,000-field cap `[V]` — [Globus Search limits](https://docs.globus.org/api/search/limits/).
- Postgres pitfalls at scale are documented: pgstac recommends disabling sorting or using short timeouts beyond millions of rows and warns that result counts ("context") are very expensive `[V]` — [stac-fastapi-pgstac](https://github.com/stac-utils/stac-fastapi-pgstac), [pgstac docs](https://stac-utils.github.io/pgstac/pgstac).
- Postgres mechanisms relevant to this design `[BK]`: JSONB + GIN (`jsonb_path_ops`) for containment queries; expression/B-tree indexes on promoted keys for range predicates (GIN does not serve `<`/`>`); `ltree` + GiST for hierarchical paths; declarative partitioning by scope/time — [PostgreSQL JSON types](https://www.postgresql.org/docs/current/datatype-json.html), [GIN](https://www.postgresql.org/docs/current/gin.html), [ltree](https://www.postgresql.org/docs/current/ltree.html), [partitioning](https://www.postgresql.org/docs/current/ddl-partitioning.html).

**API in front of the database**
- Butler shipped with clients connecting directly to the registry DB and later had to add a REST server/RemoteButler "for scaling and security reasons", reusing platform auth and signed URLs; graph building is a many-query workload that needed special consideration `[V]` — [DMTN-288](https://dmtn-288.lsst.io/DMTN-288.pdf), [DMTN-242](https://dmtn-242.lsst.io/), [SPIE 2024 paper](https://spiedigitallibrary.org/conference-proceedings-of-spie/13101/131013G/Converting-Rubin-Observatorys-data-butler-to-a-clientserver-architecture/10.1117/12.3019130.full).

**Event log / CDC for derived indexes and cross-system sync**
- OpenMetadata "captures changes to entities as events and stores them in the server database", then indexes change events into Elasticsearch `[V]` — [OpenMetadata architecture](https://docs.open-metadata.org/developers/architecture).
- Rubin: Rucio's Hermes daemon emits Kafka messages; `ctrl_ingestd` consumes them and performs Butler ingests at the destination site; `rucio-register` pushes Butler datasets into Rucio `[V]` — [Rubin Rucio–Butler integration ops docs](https://df-ops.lsst.io/usdf-applications/drp/rucio-butler-integration/index.html).
- ESCAPE/SKA noted that syncing a metadata catalogue with the replica catalogue "can be engineered async or synchronous. Is a strategic structural decision" `[V]` — [ESCAPE DIOS final meeting notes](https://indico.in2p3.fr/event/26928/attachments/70683/101471/ESCAPE%20DIOS%20Final%20Meeting-%20Draft%20Notes.pdf).

**Typed-metadata query languages compiled to SQL**
- MQL (set algebra over file sets, named queries, provenance traversal, external filters) `[V]` — [MQL docs](https://fermitools.github.io/metacat/mql.html); SLAC Datacat's query string + container glob + sort/show fields, requiring temp tables — `/home/user/datacat/README.md`; Globus exposes "a subset of the expressions supported by Elasticsearch" `[V]` — [Globus query](https://docs.globus.org/api/search/query/); existing *standard* filter languages are OGC CQL2 (STAC API filter) and IVOA ADQL `[BK]` — [CQL2](https://docs.ogc.org/is/21-065r2/21-065r2.html), [ADQL](https://www.ivoa.net/documents/ADQL/).

**Naming: hierarchical vs flat vs multi-level**
- Hierarchical POSIX-like paths: Datacat, DIRAC DFC, Onedata, Pelican prefixes (prefix ↔ signing key) `[V for Pelican]` — [Pelican overview](https://indico.cern.ch/event/1343110/contributions/6119455/attachments/2939390/5163600/Overview%20of%20the%20Pelican%20Platform.pdf). Flat `namespace:name`: MetaCat `[V]` — [MetaCat paper](https://www.epj-conferences.org/10.1051/epjconf/202125102048). ### Inferences
- **Recommended skeleton.** One stateless service (Rust or Go) + Postgres as the only required dependency; SQLite/embedded mode with the same schema subset for laptops, tests and "static catalog" exports; optional add-ons fed by a transactional outbox (CloudEvents): OpenSearch/Tantivy for text, pgvector for embeddings, Kafka/NATS only if a site already has it. This mirrors what worked for pgstac, Marquez, OpenMetadata, Lakekeeper and avoids the reindex/field-cap and multi-store consistency problems seen with search-engine- or Mongo-primary designs.
- **Metadata storage.** JSONB column validated against registered schemas, GIN for equality/containment, and *promotion* of declared keys to typed generated columns or a typed side-table for range/sort — because GIN cannot serve range predicates and unbounded sort/count are the documented Postgres failure modes (pgstac). Plan cursor pagination and estimated counts from the start; never promise exact totals.
- **Reference-data joins as a first-class feature** (Butler dimensions / MetaCat external filters / Datacat foreign metadata): model "dimension tables" explicitly in the catalog rather than duplicating run/exposure attributes onto 10^8 file rows.
- **Naming.** Use an immutable opaque ID (UUIDv7 or similar) as the primary key, a hierarchical human path (`ltree`) as a mutable alias, and derive the outward-facing forms mechanically: `catalog.schema.name` for lakehouse tools, `namespace:name` for HEP tools, OpenLineage namespace+name, URN/DOI. Systems that made the human name the key (flat scope:name, three-level) all later needed aliasing or renaming workarounds — inference, not sourced.
- **Content addressing: adopt for identity, not for storage.** Record multi-algorithm checksums and allow "same content ⇒ same replica group", but do not require content-addressed layout or chunk dedup: science files are large, immutable, already placed by site policy, and hashing is a measured bottleneck. Offer CDC/dedup only as an optional datastore plug-in for ML-style datasets.
- **Never let clients hit the DB.** Butler's retrofit is the cautionary tale; design the REST/gRPC API, pagination and bulk endpoints (COPY-style bulk registration, streaming query results as Arrow/NDJSON) on day one. Workflow engines need a *bulk snapshot/manifest* path (cf. DMTN-177, QuantumGraph) so 10^5 jobs do not each query the catalog.
- **One catalog, not two synced by bus.** Rubin (Butler⇄Rucio via Kafka), DUNE (MetaCat+Rucio) and ESCAPE/SKA (Rucio + IVOA metadata service) all ended with a metadata catalog and a replica catalog kept consistent asynchronously. Putting logical identity, metadata and replica state in one transactional store — while delegating *transfer execution* to external engines (FTS, Globus, rclone, Pelican) — removes the sync problem; this is the central architectural bet a new system can make.
- **Declarative replication policies** should be data in the catalog (rule = selector + target expression + lifetime) evaluated by a reconciler loop, with executors pluggable; lakehouse tools have nothing comparable, so this is differentiating rather than duplicative.
- **Agent interface.** Ship MCP as a thin layer over the same API with the caller's identity (OpenMetadata's pattern); expose the typed query language and schema registry as tools so agents compose metadata queries rather than relying on fuzzy search alone. Embeddings over dataset descriptions + schema docs are cheap; embeddings over 10^9 file rows are not useful — index at dataset/collection level.
- **Pitfalls checklist:** EAV tables for metadata (join explosion — Datacat needed temp tables for search); search engine as system of record; exact counts and arbitrary sorts on huge result sets; per-file ACL rows (use container-inherited policies); assuming one checksum algorithm or one auth scheme; coupling to one workflow system or one Python object model (Butler); mandatory domain core fields (STAC's geometry); requiring Kafka/ES/graph DB for a first install.

### Gaps
- No head-to-head benchmark of Postgres-JSONB vs. document-store vs. search-engine for typed-metadata queries at 10^8–10^10 file rows was found; MetaCat's and Butler's actual index designs and query latencies were not verified.
- `ltree` at catalog scale, and embedded SQLite/DuckDB modes for a *file* catalog (as opposed to table catalogs) — no production evidence found; these are design inferences.
- No evidence gathered on Rust/Go single-binary catalogs' operational track record beyond the PSDI study's selection of Lakekeeper.
- Engineering-blog comparisons of catalog architectures (2024–2026) surfaced in search were largely vendor-authored (Atlan, Dremio, Snowflake) and should be treated as partisan.

## 6. Prior attempts to unify scientific data management with modern catalog/lakehouse tooling, and lessons

### Takeaway
No project found has unified the two worlds in one system. Science projects compose two or three catalogs joined by message buses (Rubin, DUNE, ESCAPE/SKA); lakehouse projects in research labs (STFC PSDI, DOE AmSC) adopt Iceberg for tabular data and leave files outside; lakehouse vendors add path-prefix "volumes/filesets". The niche — a single open catalog with file/replica/typed-metadata depth *and* lakehouse/ML-facing standards — is unoccupied as of late 2026.

### Cited Findings
- **Rubin Butler + Rucio (in operation).** Division of labour: Rucio holds file metadata and location tracking and drives movement; Butler handles dataset search. `rucio-register` registers Butler datasets into Rucio; `ctrl_ingestd` listens to Kafka messages from Rucio's Hermes daemons and ingests arriving files into the destination site's Butler; each site has its own Butler registry; purpose-built Butler tools were needed "to integrate Rucio's data model with the Butler"; checksum computation at registration is a bottleneck where storage does not record adler32 at creation `[V]` — [Rubin ops docs: Rucio-Butler integration](https://df-ops.lsst.io/usdf-applications/drp/rucio-butler-integration/index.html), [Data Movement Model for Rubin, EPJ WoC 2025](https://www.epj-conferences.org/10.1051/epjconf/202533701129), [arXiv:2507.12955](https://arxiv.org/abs/2507.12955), [Rucio workshop 2024 slides](https://indico.cern.ch/event/1343110/contributions/6078851/attachments/2937973/5160845/RucioWKShop2024-Rubin.pdf), [SA3CC 2026 slides](https://www.amlight.net/wp-content/uploads/2026/01/SA3CC2026_-Rubin-Multi-site-Data-Movement-Wei-Yang.pdf).
- **ESCAPE / EOSC data lake (2019–2023) → SKA SRCNet.** Pilot data lake = storage services orchestrated by Rucio for astronomy/astroparticle/HEP partners; SKA's 2022 assessment: Rucio well supported and suited to offline distributed data handling, *not* suited to online/time-critical workflows, large-scale metadata needing test, metadata via plug-in back-ends; open design question whether IVOA metadata belongs inside Rucio or in a separately-synced catalogue; by 2024 SKAO describes an astronomical metadata plugin enabling discovery with existing astronomy client libraries, and a May 2026 talk still lists metadata handling and embargo control as adaptation work `[V]` — [ESCAPE data lake, EPJ WoC 2021](https://doaj.org/article/753d1a1f4a5b4322abc7e9e6858c610b), [DIOS deployment experience 2022](https://indico.in2p3.fr/event/26307/contributions/105835/attachments/69440/98054/ESCAPE%20DIOS%20Workshop,%20Deployment%20Experience,%20March%202022.pdf), [DIOS final meeting notes](https://indico.in2p3.fr/event/26928/attachments/70683/101471/ESCAPE%20DIOS%20Final%20Meeting-%20Draft%20Notes.pdf), [SKAO at Rucio workshop 2024](https://indico.cern.ch/event/1343110/contributions/6089547/attachments/2937876/5160662/JSC%20-%20DDM%20Assessment%20-%20Rucio%20Workshop%2030-09-24%20(1).pdf), [SRCNet data lake talk, May 2026](https://indico.cern.ch/event/1471803/contributions/6967407/), [arXiv:2202.01828](https://arxiv.org/abs/2202.01828).
- **DUNE:** MetaCat (metadata) + Rucio (replicas) + Data Dispatcher (delivery) as the deliberate decomposition of monolithic SAM `[V/BK]` — [MetaCat paper](https://www.epj-conferences.org/10.1051/epjconf/202125102048), [DUNE databases, CHEP 2023](https://www.epj-conferences.org/articles/epjconf/pdf/2024/05/epjconf_chep2024_03010.pdf).
- **STFC PSDI "Data Lakehouse" study (UK physical sciences; report June 2026).** Five-layer architecture; Apache Iceberg identified as "the likely winner" among lakehouse specifications; catalog = Lakekeeper (Iceberg REST); datasets such as Materials Project and OMol25 registered as Iceberg tables `[V]` — [STFC-TR-2026-011](https://epubs.stfc.ac.uk/manifestation/66674388/STFC-TR-2026-011.pdf), [PSDI lakehouse poster, Nov 2025](https://indico.ukaea.uk/event/532/contributions/896/).
- **US DOE American Science Cloud (AmSC) Data Lakehouse.** Research-data lakehouse using AWS Glue as catalog and PyIceberg for writes; early-user access only at time of the page snapshot `[V]` — [AmSC Data Lakehouse](https://amsc.energy.gov/?p=450).
- **Lakehouse vendors reaching toward files:** Unity Catalog volumes and Gravitino filesets/models — see §2 `[V]`. **ML hubs reaching toward storage:** HF Storage Buckets (Mar 2026) `[V]` — [HF blog](https://huggingface.co/blog/storage-buckets).
- **Repositories reaching toward ML/agents:** Croissant + MCP on Harvard Dataverse and Kaggle `[V]` — [MLCommons](https://mlcommons.org/2026/02/croissant-1-1-standard/).

### Inferences
- **Lessons that recur across attempts:** (1) metadata catalog and replica catalog end up as two systems, and their synchronisation (async bus vs. synchronous) becomes "a strategic structural decision" and an operational burden; (2) domain metadata standards (IVOA, dimensions) are bolted on via plug-ins late, and embargo/ACL semantics later still; (3) identity and checksum heterogeneity across sites dominates integration effort; (4) research labs adopting lakehouse tech choose plain Iceberg REST + a light catalog (Lakekeeper, Glue) — they want the *standard API*, not an enterprise governance suite; (5) lakehouse catalogs extend to files only as far as governance requires.
- **The unoccupied niche (designer's statement):** an open-source, small-deployment-first catalog whose core is *logical dataset → immutable versions → checksummed replicas across sites*, with schema-registered typed metadata and dimension/reference tables queryable at 10^8+ files through a language compiled to SQL — and whose outward faces are the data-science standards: Iceberg REST (tables, and file sets surfaced as tables-of-files), fileset/volume-style prefixes with credential vending and fsspec, OpenLineage in / PROV out, Croissant/DCAT/schema.org/RO-Crate/DataCite export, CloudEvents change feed, MCP. Nothing reviewed occupies this: Gravitino is nearest from the lakehouse side (filesets with multiple locations, models, tables) but lacks per-file/replica/metadata depth; MetaCat+Rucio and Butler+Rucio are nearest from the science side but are two-system compositions without schemas, lineage standards, discovery UI or ML objects. SLAC Datacat's own model (dataset/version/location + containers + typed metadata + crawler) is essentially the right core and mainly lacks the modern outward faces, scale engineering and standards alignment.
- **Positioning advice:** interoperate rather than replace — be registrable *as* a Gravitino/Unity/Polaris-adjacent catalog (or expose Iceberg REST for a "files" table per collection), accept Rucio/FTS/Globus/Pelican as transfer executors, and act as an OpenLineage consumer. Adoption in science historically came from one anchor experiment plus a generic design (MetaCat for DUNE); adoption in data science comes from a five-minute local install and standard client compatibility (Lance directory namespace, STAC static catalogs, Lakekeeper).

### Gaps
- No evidence found (in this session) of DataHub, OpenMetadata or Amundsen deployed as the primary catalog for file-based experiment data at a research lab, nor of any HEP experiment adopting Iceberg for event data; this is absence of search results, not proof of absence.
- No peer-reviewed "lessons learned" for the ESCAPE data lake's metadata integration, and no outcome reported for the SKA IVOA/Rucio metadata question; the May 2026 SRCNet abstract gives no results.
- The STFC PSDI and AmSC documents were seen only as search summaries; how (or whether) either handles non-tabular instrument files and replicas is unknown.
- Could not read arXiv:2507.12955 (Rubin data movement) in full; scale numbers (files/day, dataset granularity problems) remain unverified.
- Hosts that must be allow-listed for a deeper pass: arxiv.org, lss.fnal.gov, gravitino.apache.org, openlineage.io (all failed DNS resolution from this session).
